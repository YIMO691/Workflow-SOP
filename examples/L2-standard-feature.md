# 示例功能说明：收藏项目

这是教学设计与交付说明示例，没有真实执行测试。所有背景为示例假设；实际项目应替换为检查过的来源。本例展示澄清、行为切片和验收怎样放在同一份功能说明。

阅读方式：想了解人与 AI 怎样推进任务，先看 [完整运行演练](#完整运行演练)；想看最后保留的功能记录，从 [来源与现状](#来源与现状) 开始。两部分解释同一项任务，后文的验收与设计是本例唯一的详细约定。

## 完整运行演练

下面把已有四个阶段放进同一项收藏任务，展示输入、动作、交接和结果。**所有对话、工程条件、缺陷及操作都是教学假设，没有实际运行产品或测试。** 真实使用时替换为项目事实、已确认需求、实际授权和证据；不要把本例当作目标项目的批准记录。

可以在同一 AI 会话中连续完成；有授权且信息足够就继续，不需要每阶段再输入一次“开始”。人负责业务选择、权限与风险接受，AI 在授权内承担可检查的分析、实现和验证。两者共同更新原任务，不另建阶段状态表。

### 开始前：在哪里做，准备什么

在**目标项目的工作环境**中使用已选 AI 工具，先让它读到项目约定和固定版本 SOP。文件接入和首次检查统一见 [AI 接入说明](../docs/AI_COLLABORATION.md#首次接入)；不是在这个教学仓库里创建收藏功能代码。

| 需要的输入 | 由谁提供或查明 | 本例怎么用 |
|---|---|---|
| 一个问题及原始来源 | 用户给目标或现有任务；AI 读取可访问内容 | 用户想从列表找到常用项目，支持收藏与取消 |
| 项目位置、原记录和采用规范 | 用户提供可访问入口；AI 核对实际工作目录与指令 | 沿用原任务保存约定，已有文档不重建 |
| 本轮授权与资料边界 | 沿用真实用户授权和项目约定 | 教学中只讨论开发与验证，合并/发布另按实际权限 |
| 技术事实与验证条件 | AI 查代码、契约、测试和项目指南 | 登录、可见性、持久化、测试命令均需核实；不要求用户凭记忆口述 |

首次任务输入可以这样写，尖括号内容需要替换。这是输入写法示例，不自动授权业务项目操作：

```text
请按项目约定处理收藏功能。
项目与原任务入口：<实际位置>；SOP 采用版本与入口：<实际位置>。
希望项目列表支持收藏、取消，并在重新登录后保留自己的收藏。
本轮允许：<实际授权的代码、测试或文档操作>；边界：<实际限制>。
先查现有实现与测试，只询问会改变本轮结果且无法自行确认的问题。
把约定与实际结果写回原任务，不必为了采用 SOP 生成整套文档。
```

如果原任务已经写明仅在线、权限和验收，直接引用这些决定；后面的提问只是信息缺失时的示意。

### 第一阶段：理解问题与现状

**用户先给目标，AI 先查事实。** AI 应找到列表入口、登录身份来源、项目权限检查、写入与读取路径、现有测试和允许的运行环境。教学假设是已有身份与权限能力，但没有收藏记录；只有真实查到代码或约定后才能将类似内容写成事实，记录位置或来源即可。

接下来把“未知技术事实”和“未决定的业务行为”分开。例如可否复用已有权限查询由 AI 检查；是否允许离线收藏由业务需求决定。一次有意义的澄清可以是：

> AI 提问示意：离线时是否也允许收藏？若只做在线，断网时提示状态尚未确认；若需要离线操作，还要确定跨账户、权限变化和重连冲突的处理，这会扩大当前范围。
>
> 用户回答示意：本次只做在线；不做共享列表、排序或通知。

“取消收藏”和“停止等待”仍要区分，具体约定写回 [澄清与决定](#澄清与决定)。不要从“只做在线”推断可以省略超时恢复。

**这一阶段留下什么**：原任务中的事实来源、目标、范围和仍会阻断当前动作的未知。AI 可简短报告“已找到什么、还缺什么、下一步查哪里”，不必返回整份代码盘点。目标和主要边界已清楚时，进入必要设计；查得到的事实继续自己核对，不反复让用户回答。

### 第二阶段：明确结果与必要方案

**将目标变成可区分对错的结果。** 在原任务或本功能说明里维护 [AC-01–04](#目标与验收)，把实现选择和验证安排关联到这些要求，不再复制一份需求表。后文已有内容时直接引用，不重新生成 PRD、技术方案和验证计划三份文件。

| 当前要做的判断 | 本例采用的思路 | 实施前还要核对什么 |
|---|---|---|
| 刷新后仍能读到收藏 | 使用持久化关系，不仅改变按钮样式 | 实际存储位置、事务边界和读取路径 |
| 重复点击不反转或重复保存 | 写入目标状态，使用用户与项目的唯一约束 | 契约定义、并发行为与实际数据库约束 |
| 收藏不成为授权旁路 | 可信会话确定账户，继续走原项目权限检查 | 列表与直接查询都执行正确校验 |
| 超时不误报成功或回滚 | 保留结果未知，依据操作结果和顺序语义恢复 | 是否有可观察终态，如何处理迟到响应与新的相反意图 |

技术理由与边界见 [关键设计](#关键设计与理由)。如果终态查询或顺序语义尚未明确，AI 应指出 AC-04 的依赖缺口，先查现有协议或给出待决定方案；不能写一个“自动重试”按钮就认为设计完成。可继续无依赖的已授权工作，但不能宣称整个功能已就绪。

随后按 [实施增量](#实施增量示意) 安排先后，将每片行为连接到 [验证场景](#验证安排)。先列当前增量需要的检查，不提前编造后续接口、命令或测试结果。

**什么时候直接进入实现**：当前增量的结果、边界、必要决定和验证方式已清楚，前提成立且已有实施授权。普通可逆技术细节由 AI 在这些约束内推进；只有新的业务选择、权限缺口或重要风险才找实际责任人处理。已有授权无需再统一批准一次设计。

### 第三阶段：小步实现与验证

**AI 在项目中执行，人看重要发现与实际证据。** 默认沿用当前会话和原任务；这段循环不要求安装单独的 Harness、规划器或固定数量的 Agent。

1. **选一个能观察结果的增量**：例如打通收藏、保存后读取和账户隔离。核实该增量依赖后，在项目允许的分支或工作副本修改相关实现及测试，不覆盖已有改动。
2. **让测试能抓到目标缺陷**：以 AC 的预期为依据，检查收藏后的真实读取、另一账户访问与重复设定。适合测试先行时先观察预期失败再修复；沿用其他方式时也要说明检查如何区分正确与错误，不能只断言函数被调用。
3. **实际运行适用检查**：使用从目标项目查到的命令与环境，检查报告中目标场景是否执行。数据库约束要有对应证据，不能从纯内存测试外推；界面和跨端行为按风险补检查。
4. **根据失败改变下一步**：先区分环境失败、实现缺陷、测试预期错误和需求歧义；修复后重验原问题及受影响范围。重复失败且没有新证据时调整调查方向，不盲目增加重试次数。
5. **把有用结果留回原任务**：记录实际改动、观察、对应版本/环境、可访问证据与剩余范围。当前增量通过只支持这片行为，再进入下一片；不必每次工具调用都填写记录。

例如故障注入场景是“服务端写入提交后，响应在返回前丢失”。**若实际观察到**界面直接提示已回滚，这是需要检查的行为缺陷。应核对请求时序、持久化结果、操作归属及界面处理，再按既定恢复契约修复；重验未知状态、迟到响应和后续取消，不能只再次跑正常收藏。这个例子不是实际故障观察，也不假设项目已经具备故障注入设施。

AI 的进度说明可以短而具体：当前正在支持哪项验收、已经观察到什么、哪个问题会影响继续。只有命令退出成功、没有目标场景结果时，应说明“检查尚不足以支持该项验收”，继续查测试发现与过滤条件。

用户此时只需处理确实需要自己的决定；可以随时提供纠正或新目标。若提出离线收藏，则走后文 [变更与重验](#变更与重验示意)，更新原约定及受影响检查，不把它当作顺手补充的界面细节。

### 第四阶段：评审交付与反馈

**先提供可审阅的完整改动，再判断可以交付什么。** AI/实施者按当前目标与实际差异自检，关联原任务、代码、契约、文档和验证证据。跨多次提交或仍有未提交改动时，明确审阅范围；不能只审最后一个提交就报告整个任务已审。

按项目责任与风险安排评审。本例涉及账户与权限，需要合适的独立检查；评审者读取相同需求和完整差异，不以作者改一段提示词代替独立性。意见写清场景、影响和依据，修复后复查；方法见 [工程规则](../docs/ENGINEERING_RULES.md#评审与清理)。

一个具体审查问题是“服务端信任客户端提交的账户”。即使代码符合先前计划，也仍违背可信会话的约定。应修正错误计划与实现，检查其他账户读取、伪造身份输入及原有正常行为；不以“按计划开发”关闭意见，也不修改验收来接受越权。

交付汇总可以留在原任务或关联 PR，填写真实结果后再形成结论：

```text
本轮结果：<支持了哪些行为，哪些仍未完成>。
实际验证：<场景、实际观察、版本/环境和证据入口>。
评审情况：<真实审阅范围、发现与复查结果；未做则说明>。
当前限制：<阻断项、尚未验证项、下一步及实际接手安排>。
交付状态：<开发、验收、合并和发布各自发生了什么>。
```

如果权限撤销后查询还没有被验证，AC-03 就仍缺依据，不能宣布整个收藏任务完成。如果后续实际实现、适用验证和必要评审均支持目标，再按项目安排验收与交付；本教学文件没有这些结果，始终不能改称“已通过”。

**合并与发布按实际授权分别进行。** 代码评审通过不等于允许发布。真实项目准备发布时，在已有交付/发布记录安排与本次变化有关的观察，例如收藏写入错误、未知状态持续出现及权限拒绝是否异常；信号来源、观察范围/时段、判断条件和接手人由实际环境决定，不凭示例填写数字或默认新增监控系统。依据见 [发布观察](../docs/WORKFLOW.md#发布后的观察与反馈)。

发现异常时保留脱敏事实，按已有权限回退、停用或修复；未具备处置权限就交由实际承担者决定。开发完成、已发布和观察中分别记录。最后把流程采用反馈写回原任务，例如哪项检查发现了遗漏、哪段记录造成重复；有证据再提议修改 SOP，不由一次教学演练宣称效率提升。

### 卡住或换工具时怎样继续

| 实际情况 | AI 可以继续做什么 | 需要人参与的部分与恢复依据 |
|---|---|---|
| 缺少测试环境或命令无法执行 | 查失败阶段、前置与允许的修复方式；继续不依赖该环境的工作 | 需要新资源/权限时由实际承担者处理；恢复后实际执行受阻检查 |
| 同一缺陷多次修复仍失败 | 保留症状与已尝试方法，重新区分原因，必要时请求可用协作 | 人补充不可发现的领域事实或协调依赖；新证据决定路线，不以轮数强行完成 |
| 用户暂停、会话中断或更换 AI | 把当前目标、决定、差异、证据、未决项与外部动作留在原记录 | 恢复者核对真实工作副本和仍适用授权；不能只凭上一会话“已完成”继续发布 |
| 新需求改变范围 | 分析与现有约定的差异及影响，继续不受影响的已授权工作 | 实际业务决定人确认取舍后更新原需求和重验范围 |
| 验收或发布责任暂不明确 | 查项目已有安排，整理可交付内容及缺口 | 只暂停依赖该责任的验收/发布，交项目负责人协调 |

换工具时可给出简短恢复要求：读取原任务与项目约定，核对当前差异和证据，从尚未完成的增量继续；不要重写需求或重复已发生的外部动作。交接字段和核对方法统一见 [中断与交接](../docs/AI_COLLABORATION.md#中断与交接)。

### 哪些内容可以省略

- 已有清楚需求与项目接入：跳过示意访谈和首次接入检查，直接核对当前增量。
- 小缺陷：按 [标签修复案例](L1-bugfix.md) 在原记录写目标、改动和检查，不必套本例全部章节。
- 不涉及部署或运行：省略发布观察，不因此省略改动本身需要的验证。
- 没有具体卡点：不启用额外技能。需要时按 [技能推荐](../skills/README.md) 选澄清、计划、排查或评审方法，结果回到同一任务；没有实际安装或调用就只称参考。

## 来源与现状

示例需求：用户希望在项目列表中快速找到常用项目。假设已有用户登录和项目可见性校验，但没有收藏记录。沿用现有权限模型，不改变项目授权；账户从可信会话取得，不能信任客户端自行指定账户。

## 澄清与决定

先查登录、权限与持久化能力，再决定用户行为。教学情境中约定：仅在线收藏，不支持离线修改；“取消收藏”指目标收藏关系不存在，“停止等待”只表示客户端不继续等待请求。服务端保存后丢失响应时，停止等待不保证撤销；因此不继续讨论范围外的离线合并策略，也不把按钮恢复旧样式当成远端回滚。

这些是示例约定，不是实际用户批准记录。真实需求若不同，修订对应验收和设计，不照抄本例作为授权。

## 目标与验收

- AC-01：当前有权访问的项目可收藏和取消；重复设定同一目标状态不产生重复关系或意外反转。
- AC-02：重新登录后仍能看到自己的收藏；不能读取其他用户的收藏。
- AC-03：权限被移除后，收藏不会让用户绕过项目可见性校验。
- AC-04：写入结果未知时不误报保存成功或已回滚；恢复显示有该操作结果与当前状态的依据，旧响应不覆盖后续有效操作。

本轮不做离线修改、收藏排序、共享列表或消息通知。修改范围为收藏行为、相关接口与 UI，以及必要测试；具体路径由实际项目约定。

## 关键设计与理由

收藏关系使用用户与项目组合的唯一约束；写入表达目标状态，而不是每调用一次就翻转。查询仍经过原有项目权限校验，避免收藏表成为另一份授权源。重复同一操作与用户发起新的相反操作需要区分，顺序与并发语义通过目标项目的契约明确。

Client 区分明确拒绝与结果未知。只有取得可信终态时才按约定协调显示；超时先保留未知，按已有协议查询同一操作并协调资源视图。若项目没有终态或顺序保证，就需要补设计或明确阻断 AC-04，不能凭一次读到旧状态宣称请求失败、直接重复写入或假称能力已存在。Server 的幂等、原子边界与权限检查需实际验证。

两端设计可在此说明，暂不拆 CLIENT-SDD / SERVER-SDD。接口字段引用实际项目可执行定义；本示例不编造仓库链接。取舍依据见 [超时与恢复规则](../docs/ENGINEERING_RULES.md#超时重试与结果未知)。

## 实施增量示意

| 增量 | 对应验收与可观察结果 | 真实依赖 |
|---|---|---|
| 收藏、保存后读取与最小界面 | AC-01 收藏部分、AC-02：同账户重新登录可见，其他账户不可见 | 已有身份/权限接口和持久化设施经核实 |
| 取消与结果未知的处理 | AC-01 取消部分、AC-04：取消后关系不存在；迟到响应不覆盖后续操作 | 上一片的写入/读取契约；操作结果与顺序语义明确 |
| 撤销权限后的完整行为核对 | AC-03：已收藏也不能越权读取；相关回归 | 原项目权限变更能力和实际收藏实现 |

第一片通过不能代表取消、超时和权限撤销已经通过。团队可将第三项检查提前或并入实现；表格不是固定派工顺序，支撑性工作与真实依赖按项目情况安排。

## 验证安排

下表都是待执行的检查计划。预期来自上述约定，不从实现结果反推；权限相关分支需要适当独立评审。

| 场景 | 可区分的错误 | 预期与观察位置 |
|---|---|---|
| 正常收藏、取消后重新读取 | 只改 UI 或取消未持久化 | 保存后可见、取消后关系不存在，实际 API 与界面读取共同支持 AC-01 |
| 重复设定收藏状态 | 重复行或错误翻转 | API/读取行为符合 AC-01；必要时核验实际数据库唯一约束 |
| 同账户重新登录、另一账户读取 | 只保存内存状态或越权 | 刷新/登录读取与可信身份校验支持 AC-02 |
| 已收藏后撤销访问权限 | 收藏绕过权限服务 | 列表及直接读取都遵守 AC-03，不能只测按钮隐藏 |
| 写入已提交但响应丢失，再有迟到响应或取消意图 | 超时即误报回滚、旧响应覆盖新意图 | 按已确定的故障时序核验操作结果和显示；缺可观察终态则 AC-04 未验证 |

## 变更与重验示意

假设实施中有人提出“离线时也能点击收藏，联网后自动同步”。这是新的教学变更请求，尚未确认，不改变本例当前的“仅在线”约定。它改变行为与冲突处理，不能当普通 UI 细节直接接入。

| 需要判断的影响 | 应采取的动作 |
|---|---|
| 当前需求不包含离线修改 | 向实际业务决定人说明影响；若接受，在原目标/验收中修订，保留来源与理由，不另复制一份 PRD |
| 离线期间可发生退出账户、权限撤销或多次相反意图 | 明确待同步数据归属、重新鉴权、同一操作与新意图的区别，以及冲突选择；这些未知阻断离线同步实现 |
| 原设计仅处理在线请求 | 核对本地持久化、同步协议及恢复能力，重新安排受影响增量；不要假定原有终态查询足够处理离线队列 |
| 若已有证据仅覆盖在线路径 | 重新评估 AC-01–04：补离线重启、切换账户、权限撤销和乱序同步；原在线检查是否沿用取决于实际差异及依赖变化 |

如果这个请求暂缓，继续完成原范围中不受影响的工作，并记录暂缓去向。真实业务决定前可以检查工程能力、分析方案，不能把未批准的离线行为写成已实现。无论采用与否，交付结论都说明适用的需求版本；更新文件日期不能替代重验。本示例没有上述测试的运行证据。

## 评审与交付记录示意

假如计划要求直接信任请求中的账户，而本规格要求可信会话，评审应指出计划错误，按已确认身份规则修计划与实现并重验；不能因为实现符合计划就关闭越权意见。多次提交的同一增量提供完整差异，工作区尚未提交的内容也明确纳入审查范围。

如果实现已完成但还未验证权限撤销后的查询，应写明：“收藏主路径已实现；权限撤销行为尚未验证，AC-03 未确认，当前不能宣布任务完成。下一步补充该场景的实际测试与评审。”这句话只示范实际出现该情形时的写法。

当前示例没有执行代码或测试，也没有验收。实际结果在本文件或关联交付 PR 中择一汇总；不能将上表的预期、模拟措辞或审阅建议填成已通过。
