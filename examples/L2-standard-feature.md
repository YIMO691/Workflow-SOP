# 示例：同一份收藏功能文档怎样持续更新

这是两次提单的文档编辑演示，没有实际产品实现、测试或批准。模块名是教学假设，真实项目应替换为检查过的代码入口和证据。

## 首次提单

教学任务 A：让用户收藏条目，重新登录后仍能看到；支持取消收藏。AI 先检查项目现状，再在项目允许的文档位置建立“收藏功能.md”，加入相关入口。以下展示四部分应写的内容。

### 需求与边界

来源：教学任务 A。状态：拟变更，尚未实现。

- 收藏按账户保存，重复设为已收藏不增加重复关系；取消后重新读取应不存在。
- 列表和直接读取都检查当前权限，收藏不绕过访问控制。
- 写入超时不能显示为确定失败或已回滚；需要区分成功、明确拒绝和结果未知。
- 本次不做离线收藏、共享列表或批量操作。

### 实现说明

拟议责任：客户端展示状态并归属响应；服务端校验账户/权限、保存收藏关系并提供读取。真实接口、持久化设施和唯一约束尚未核对，因此不填写虚假的源码链接。

写入表达“设为收藏/取消”，避免重复请求导致反复翻转；去重、顺序和响应归属仍需结合项目契约确定。写入超时后查询同一次操作或核对可观察终态；一次读到旧值不能证明迟到写入不会发生。新意图之后到达的旧响应不能覆盖新选择。

### 验证与遗留

以下均为待执行场景，无通过记录：

| 要确认的行为 | 怎样区分正确与错误 |
|---|---|
| 收藏、取消与重复请求 | 保存后重新读取，并核对实际唯一约束；不能只检查按钮变化 |
| 跨会话与账户隔离 | 同账户重新登录可见，另一账户不可读 |
| 权限撤销 | 已收藏后撤权，列表和直接读取都遵守当前权限 |
| 响应丢失及迟到 | 在写入已提交、响应未取得的时序下检查恢复；旧响应不得覆盖后续取消意图 |

遗留：实际操作终态、权限接口、恢复与顺序语义待核对；相关条件未具备前不承诺这些行为已实现。执行后在这里补真实版本、结果和证据入口。

### 变更记录

教学任务 A：补充收藏、取消与失败恢复的拟议约定；产品实现与验证未执行。真实项目交付后关联实际 PR，并将已实现内容更新为当前说明。

## 后续提单：增加收藏数量上限

教学任务 B：希望每个账户最多收藏 100 条，已收藏条目的重复请求仍成功，取消后可以再次收藏。100 是示例设定；是否接纳及旧数据如何处理仍由实际业务决定。本例只演示如何在**原“收藏功能.md”**修改以下位置。

| 原章节 | 本次修改 |
|---|---|
| 需求与边界 | 在“本次拟变更”补上限及达到上限时的反馈；明确已有超过上限的数据如何处理，未决定前保留缺口 |
| 实现说明 | 核对服务端怎样保证并发下不超限、重复请求是否先判断已有关系；客户端提示不能替代服务端约束。仅更新受影响逻辑与实际代码入口 |
| 验证与遗留 | 增加 99→100、100→新增被拒、100→重复收藏不报超限、取消后可新增，以及并发争抢最后一个名额；旧数据迁移按最终约定补查 |
| 变更记录 | 关联任务 B，记录增加上限的原因、最终实现和验证入口；保留任务 A 的重要理由 |

任务 A 的旧验证即使曾在真实项目通过，也不证明任务 B 的上限与并发正确。未受影响的有效内容和人工补充保留，旧证据按实际影响复查；不另建“收藏功能第二版.md”，也不复制一套需求、设计和测试报告。

实施后正文应反映实际有效规则，未完成提案仍明确标注；真实提单/PR 与文档互相链接。本文两次提单均未实际执行，不能用于宣称功能交付。
