# 操作正反例：从记录到代码生成

以下全部是虚构教学片段；数字、版本和文件名仅用于说明写法，没有执行真实业务验收。最后一例附带可运行的教学程序，其检查范围与真实项目分开。发现同类问题时修订原记录，不另建检查报告。

## 验收只有评价词

**不足的写法**：“AC-01：收藏功能正常，超过上限时合理提示。”执行者不知道上限、观察位置和失败后允许发生什么。

**可裁决的写法**：假设已确认上限为 100。用户已有 100 个收藏，再收藏一个未收藏对象时，服务拒绝新增，最终收藏数保持 100，界面显示上限提示且该对象仍为未收藏。

由此可设计一次明确检查；99 条时新增、并发新增及重复请求是否需要单列，取决于实际规则与失败后果。100 是本例假设，不能替业务决定数值。判断标准见 [开始工作](../docs/WORKFLOW.md#开始工作)，记录位置见 [功能说明模板](../templates/SPEC.md#需求与边界)。

## 把计划或旧结果写成通过

**不足的写法**：“V-01 对应 AC-01，测试通过。”实际只列了用例；或者证据属于上限还是 50 的旧实现，却改个日期继续引用。

**如实的写法**：

| 当前事实 | 记录怎样写 |
|---|---|
| 场景已写，环境尚未就绪 | V-01 / AC-01：未执行；缺测试环境；上限拒绝行为尚无验证结果，环境就绪后执行 |
| 当前上限拟改为 100，旧结果验证的是 50 | 旧结果保留其原版本；V-01 标记待重验，不能据此宣布新上限通过 |
| 后来完成了实际检查 | 填写真实版本、前提、实际观察和证据位置，再说明能支持的规则与未覆盖范围 |

第三行是填写指导，不是本例已执行的声明。文档检查通过也不能替代业务场景结果。适用规则见 [验证模板](../templates/VERIFICATION.md#结果与遗留) 和 [失败诊断](../docs/ENGINEERING_RULES.md#检查没有给出结论时)。

## 文件齐全但维护入口断链

**不足的写法**：PR 只说“文档见 docs”，四份文件各自存在；功能说明链接模板文件，验证记录未说明对应版本。后来者无法定位本次规则的真实实现和证据。

**可维护的写法**：原提单/PR 链接“收藏功能-功能说明.md”；入口的 AC-01 关联实际限额处理章节、权威配置定义与 V-01 场景，相关记录链接回入口并注明适用版本。模板链接在复制后换成项目实际路径，缺失内容写明影响。

若只是独立文案修复，原 PR 中的目标、实际修改、检查结果及代码位置就可承载记录；受影响的既有说明同步更新。判断依据是 [载体选择](../templates/README.md#按现状选择载体) 与 [交付条件](../docs/WORKFLOW.md#交付与后续)，文件数量不证明完成。

## 把异步研究变成一次实现

这是操作演示：假设要给一个列表增加刷新，允许新请求取代旧请求，窗口关闭后结果不得继续展示。假设项目已有请求身份和生命周期机制，真实任务必须先查证这些前提。示例不是排行榜业务源码，没有运行游戏、网络或实际界面。

### 一次任务怎样开始

用户提供业务目标和工程入口即可，执行者沿 [实施步骤](../docs/WORKFLOW.md#把研究用到一次代码生成) 自行查事实、选择适用帮助并实施。下面是可直接改写的任务描述；不要求用户把每一步分别发给 AI。

```text
在当前项目完成列表刷新功能，沿用项目规范和有效 SOP 版本。
先定位数据来源、请求入口、窗口生命周期和已有异步机制，记录会影响实现的事实与未知。
结合当前风险选择适用方法：先完成一个请求到展示的增量，同时处理相关失败与清理。
在扩展其他入口前执行能区分正确与错误行为的检查；事实不足补查，设计错误改设计，再修实现。
随后完成整个任务范围及必要回归，更新原功能/分端/验证记录。
交付时说明哪条事实或哪次反馈改变了哪处代码，以及实际验证范围；不把本教学例子记成项目验证。
```

### 从研究判断到实际代码

候选判断是“仅写正常路径容易遗漏时序和清理”。本例将其作为要检验的工程假设，不引用未核实的论文效果统计。

| 动作 | 本例具体内容 | 真实项目应留下什么 |
|---|---|---|
| 先查事实 | 刷新是否可替代、何时销毁、谁拥有请求状态、已有取消是否阻止迟到结果 | 真正读取的文件/符号、版本和有关结论；不存在的机制不能编造 |
| 定义行为 | 新意图优先；失效窗口不展示；初始化失败能退出忙状态；旧请求不能清除新请求状态 | 原功能说明中的相关规则或已存在的验收 |
| 选择写法 | 请求身份和窗口有效性共同约束展示；初始化进入清理保护；收尾只处理自身状态 | 端内实现选择、理由和实际机制，不要求照搬 Python token |
| 检查首个增量 | 按下表主动控制返回/失败次序，观察显示内容和忙状态 | 实际命令、版本、观察与未覆盖范围 |
| 修正并扩展 | 从失败定位保护范围或状态归属，修复后再扩展同类入口 | 修复差异、重验及后续完整范围；尚未执行不能填通过 |

对比 [可运行源文件](async-refresh-demo.py) 中两个函数：`unsafe_refresh` 故意在保护范围外初始化、无条件展示和清理；`guarded_refresh` 保护初始化，并核对窗口与请求身份。错误版本是作者构造的反例，不是某个模型的实测输出。

### 运行并读懂结果

前提：已有 Python 3.10 或以上版本；工作目录为本仓库根目录。命令只输出 JSON，不访问网络或写文件；要留证据时按所在项目约定保存输出，不默认写入业务工程。

```powershell
python -B examples/async-refresh-demo.py
```

驱动程序手动推进协程，在指定暂停点返回值或抛异常。它验证选定次序下的状态行为，不模拟实际事件循环、线程、取消传播或 UI 资源。

| 场景与独立预期 | 故意错误版本 | 修正版本 |
|---|---|---|
| 正常返回：展示结果并退出忙状态 | 通过 | 通过 |
| B 先于 A 返回：只展示新请求 B | 失败：旧结果覆盖 | 通过 |
| 窗口关闭后返回：没有展示写入 | 失败：仍写失效窗口 | 通过 |
| 初始化抛异常：退出忙状态，能再次刷新 | 失败：忙状态残留 | 通过 |
| A 成功时 B 仍等待：保留 B 的忙状态，之后展示 B | 失败：清除 B 的状态 | 通过 |
| A 失败时 B 仍等待：错误可见，B 仍能完成 | 失败：清除 B 的状态 | 通过 |

上表为 2026-09-16 对本例的实际运行结果：同样 6 个场景各运行于两种写法，错误版本 1 通过、5 失败；修正版本 6 通过。程序退出码 0 表示该对照符合预期，**不表示错误版本也通过，更不是 12 项业务验收通过**。异常仍传播给调用方，例子没有实现用户错误提示或真实取消恢复。

### 在下一次真实开发中怎样使用

在实际刷新代码的首个增量中，复用项目既有测试框架构造适用次序，再查真实窗口/取消机制与联调。若实际业务禁止并发刷新，或关闭后仍必须提交结果，先调整场景与设计，不能直接复制本例。

在原任务留一段真实记录，例如“哪处入口证实了请求归属 → 采用什么选择 → 哪次反馈改变了哪处代码 → 对应检查与限制”；示例句不是待复制的通过结论。没有帮助或增加负担时据实写出，下次缩减或删除相应步骤。

本例只能展示怎样把一个风险转换为可执行检查，以及两种已写好代码的差异。它不能证明研究指导导致 AI 生成改善、单独哪项方法有效或长期有净收益。真实任务的采用证据按 [反馈方式](../docs/WORKFLOW.md#用实际任务修订流程) 保留，不把本地演示当作 P3 真实采用。
