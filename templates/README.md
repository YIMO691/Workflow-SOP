# 记录选择与写作参考

先使用已有任务或项目文档，只补缺少的信息。表中的文件是可选模板，中文名称用于日常交流，括号内名称与现有文件路径保留兼容。拆分规则见 [完整流程](../docs/WORKFLOW.md#约定与文档选择)。

## 各文档解决什么问题

| 需要记录什么 | 模板 | 何时使用 |
|---|---|---|
| 一个改动的目标、边界与结果 | [任务说明（TASK）](TASK.md) | 原任务卡或 PR 已能承载时直接在那里写 |
| 同一功能的需求、必要方案与验收 | [功能说明（SPEC）](SPEC.md) | 已有记录不足以说明，但尚无须分开维护 |
| 用户行为、业务规则与验收预期 | [需求说明（PRD）](PRD.md) | 需求需要独立维护或协调 |
| 职责、契约、取舍与恢复 | [技术方案（SDD）](SDD.md) | 设计需要独立讨论或维护 |
| 场景、环境与验证协作 | [验证计划（TEST-PLAN）](TEST-PLAN.md) | 验证需要单独安排 |
| 实际结果、证据与遗留 | [交付记录（DELIVERY）](DELIVERY.md) | 原任务/PR 不便汇总多方结果 |
| 重要选择及长期理由 | [重要决策（ADR）](ADR.md) | 以后缺少理由会影响维护判断 |
| 实际命令、边界与责任安排 | [项目约定（PROJECT-RULES）](PROJECT-RULES.md) | 初次接入或项目约定变化时补充 |

以下是按需阅读的写作参考，无须先读完才能开始任务。复制模板时保留实际内容，移除提示和不适用章节。

想看记录怎样随工作逐步形成，先读 [完整运行演练](../examples/L2-standard-feature.md#完整运行演练)；需要字段写法时再查对应模板，不先填满所有文件。

## 如何使用模板

1. 先判断已有任务或文档能否承载；能承载时按表补信息，无须新建同名文件。
2. 需要独立记录时，将所选模板内容放入目标项目允许的位置，替换标题和提示，删除不适用章节。保留现有编号、责任与状态入口，不再登记一份。
3. 把仓库内的相对示例链接换成目标项目可访问的固定来源，或在掌握写法后移除教学链接；直接复制相对路径到另一仓库可能断链。实际需求、方案和结果相互引用一个维护位置。
4. 计划写预期，结果写实际观察。模板表格中的提示不是数据；不要保留占位行后再填写“通过”。更新时按 [文档维护规则](../docs/WORKFLOW.md#保持文档有效) 核对受影响内容。

例如已有功能说明已包含业务验收，独立技术方案只引用该验收并解释实现选择；验证计划引用同一验收安排场景，实际执行结果在原任务或交付记录汇总，不再复制三份验收表。

## 名称与方法的区别

PRD 指 Product Requirements Document；本仓库的 SDD 指 Software Design Description，SPEC 用于单份功能说明。团队已有文档名称可继续使用，关注内容与维护位置，不需要改名才能采用流程。

TDD 通常指 Test-Driven Development（测试驱动开发），是测试、实现与重构的开发方法，不是第三份必交文档；团队若用它表示 Technical Design Document，则映射到技术方案。Specification-Driven Development（规格驱动开发）也可能缩写为 SDD，讨论方法时写全称，避免与设计文件混淆。来源见 [方法说明](../docs/SOURCES.md#文档实践的定向核对)。

项目明确要求 SRS（软件需求规格说明）时按要求组织软件行为与约束，需求说明引用或复用它。RFC（征求意见提案）用于讨论未决方案，可留在原任务/技术方案；重要结论按需保留为决策记录。这些名称并非新旧替代关系。

## 三种方法如何配合

需要检查设计内容时参考 arc42，需要解释关系时使用 C4，需要保留重要取舍时写 ADR。MADR 是 ADR 的一种 Markdown 写法，不再增加一层文件。来源、版本及实读限制见 [来源登记](../docs/SOURCES.md#文档实践的定向核对)。

### 用 arc42 组织技术方案

arc42 是架构内容框架；技术方案模板按问题合并其主题，不要求复制 12 章。C4 是其中可选的视图表达，ADR 保存决定理由，三者共用同一设计上下文。

| 技术方案模板的位置 | 对应 arc42 关注点 | 写完后读者应能判断 |
|---|---|---|
| 依据与设计约束 | 目标、约束、质量驱动（1、2） | 哪些需求和事实真正限制方案 |
| 边界、责任与契约 | 上下文、方案策略及结构（3、4、5） | 谁负责、依赖谁；必要时再定位代码模块 |
| 运行场景与失败处理 | 运行及相关跨切面概念（6、8） | 正常和失败时怎样协作、恢复 |
| 部署与演进 | 部署（7） | 运行单元落在哪里，环境差异是否影响结论 |
| 取舍、验证关联与开放问题 | 决策、质量、风险（9、10、11） | 为什么选、如何检验、还有什么未解决 |

术语有歧义时使用原规格的词汇表（12）。这只是内容定位，不是要求每行增加一份文件；C4 容器视图也不能替代必要的源码模块解释。完整写法见 [示例设计](../examples/L3-complex-feature/SDD.md)。

### C4 与决策记录

C4 视图标明范围、元素类型与职责、关系方向和含义；技术/协议未知就注明。上下文图看人和系统，容器图展开应用与数据存储等运行单元，容器不等于 Docker；不要求画齐四层，也不据图新增服务。查看 [两张 C4 图](../examples/L3-complex-feature/SDD.md#c4-视图) 与 [完整 ADR](../examples/L3-complex-feature/adr/0001-use-async-export-job.md)。

HTTP API 可引用项目支持的 OpenAPI，其他通信使用已有 Proto/Schema；技术方案解释语义与兼容，避免抄写字段。契约存在不代表实现已经符合。ISO 需求、架构描述和测试文档标准仅在项目明确需要时核对；本模板未做逐条符合性审计或认证。
