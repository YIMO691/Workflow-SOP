# 文档用法

日常只需 [功能说明](SPEC.md)：需求与边界、实现说明、验证与遗留、变更记录。AI 随工作更新，已有格式直接沿用；具体职责以 [工作指南](../docs/WORKFLOW.md#维护功能说明) 为准。

## 如何使用模板

1. 先找原功能文档并核对现状；找不到合适记录的新功能才建立文档，放入项目已有文档位置并加入相关入口。
2. 替换模板提示，使用真实任务、代码与证据链接。复制到其他仓库时修正相对路径或删除教学链接，不保留占位内容作为结果。
3. 后续提单只修改受影响章节：正文保持当前，变更记录解释重要调整。示例见 [首次开发与后续修改](../examples/L2-standard-feature.md)。

独立小修复可在原提单或 PR 留痕；改变已记录行为或设计时同步功能文档。一般不另建任务说明或交付报告。项目命令、资料边界等共用信息缺失时，才补 [项目约定](PROJECT-RULES.md)，不按任务重复填写。

## 方法按需参考

| 你需要补充什么 | 可以借鉴什么 |
|---|---|
| 设计遗漏运行、部署、质量或风险 | 用 arc42 的相关问题检查“实现说明”；不要求复制完整章节 |
| 人、系统、应用和数据存储关系难以说明 | 按需画 C4 视图，标清范围、职责和关系；不要求四层齐全 |
| 后来的人需要知道为什么这样选 | 在实现说明记录方案、理由、代价和验证方式；重要演进记入变更记录。独立决策确有维护价值时才用 ADR/MADR |

PRD 和技术设计文档是内容载体，TDD（测试驱动开发）是方法，均不是每次必须生成的文件。SDD 可指设计文档或规格驱动开发，使用时说明具体含义；团队已有名称继续沿用。

需求、设计或多人验证确实需要独立维护时才拆出该部分，原章节改为引用；不用先挑一整套模板。上述方法的版本、实读范围与限制见 [来源说明](../docs/SOURCES.md#文档实践的定向核对)，设计取舍的简短例子见 [异步导出](../examples/L3-complex-feature/README.md)。
