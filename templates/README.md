# 文档用法

双端功能使用一个功能入口，关联客户端实现、服务端实现和验证与验收。已有分端手册、需求与测试文件直接复用，不为匹配模板重新建一套。维护规则以 [工作指南](../docs/WORKFLOW.md#维护功能说明) 为准。

## 四类文档

| 模板 | 回答的问题 | 内容的维护位置 |
|---|---|---|
| [功能说明](SPEC.md) | 为什么做、规则是什么、整条链路在哪里 | 需求与验收的共同来源；关联两端与验证，保留重要变更理由 |
| [客户端实现](CLIENT.md) | 用户操作怎样变成请求，结果怎样呈现 | 界面、状态、数据同步、失败恢复与客户端代码入口 |
| [服务端实现](SERVER.md) | 请求怎样校验、执行并持久化 | 业务处理、数据归属、权限、并发、恢复与服务端代码入口 |
| [验证与验收](VERIFICATION.md) | 哪些规则实际检查了，结果支持什么 | 场景与实际结果；引用测试源码、CI/人工证据和遗留事项 |

协议、Schema、配置和测试源码以项目原定义为准；文档解释其用途、约束及调用关系，不抄完整字段表。共同业务规则只在功能说明维护，两端引用规则并解释实现。发现文档和代码冲突时记录差异、核实当前约定，不能直接把代码现状当作正确需求。

## 如何使用模板

1. 找原功能入口及相关记录，判断涉及哪些端。新双端功能缺少记录时才建立上述四类文档；一端功能不建无关端文档，独立小修按原提单或 PR 留痕。
2. 按项目已有目录、名称与格式保存。例如以“收藏功能-功能说明.md”为入口，其余文件用同一功能名标识。已有测试计划和验收记录可同时链接，不强制合并。
3. AI 先根据事实整理当前增量所需内容，再随实施补实际规则、代码位置和证据；用户无需逐项填写模板。模板里的相互链接仅为本仓库导航；复制后改成项目实际文件名和锚点，删除教学说明，核对所有链接。没查到或没执行就写明缺口。
4. 功能说明加入模块索引，链接两端和验证；各文档链接回入口。提单/PR 链接入口，重要变更记录反向关联提单和最终提交。不同仓库使用受权限保护的实际链接和各自版本，不复制私有内容到公共位置。
5. 后续改动先梳理影响，再更新受影响章节与证据；不按提单复制“第二版”。轻量工作如何交付见 [真实维护案例](../examples/completed-maintenance.md)；双端复杂行为见 [收藏功能入口](../examples/L2-standard-feature.md)。

最小充分需求放在功能说明的“需求与边界”，重要假设放在“重要决定与待定事项”，复杂度理由放在涉及端的“失败恢复与取舍”，环境和实际结果放在验证记录。它们是原章节里的必要信息，不增加 MSS、假设台账或质量契约等独立文件。

文件数量不是验收条件：已有文件能清楚承担某项职责就沿用，未涉及部分说明依据。四类记录不是四份重复报告；通常不再新建任务说明、测试计划、交付报告或决策文件。共用命令和资料边界缺失时，才补 [项目约定](PROJECT-RULES.md)，不按任务重复填写。

## 按现状选择载体

先判断现有记录能否回答对应问题，再决定是否新增文件。功能小且由同一人一起维护时，可以在一份功能文档中用章节承担四类职责；项目已有分端格式时继续沿用。有独立维护者、独立变更节奏，或篇幅已妨碍定位时，再拆出相关部分并链接回入口。

| 当前情况 | 怎样处理记录 | 仍需核对什么 |
|---|---|---|
| 小型双端新功能，还没有记录 | 按项目约定建立功能入口，相关职责可放在同一文件的不同章节 | 规则、两端处理、契约和验证之间是否能对应 |
| 已有需求与测试记录，只缺客户端说明 | 补涉及端的实现信息，入口链接原需求与测试 | 新说明是否对齐实际版本和共同契约 |
| 仅改服务端配置，客户端代码不变 | 更新受影响的规则、服务端说明及验证，记录客户端未改的依据 | 新值或错误行为是否影响旧端假设 |
| 独立小修或文档维护 | 在原提单/PR 写目标、变更和证据；受影响的既有文档同步更新 | 实际结果是否支持本次目标 |

验证深度按 [工程触发条件](../docs/ENGINEERING_RULES.md#验证覆盖与方法) 判断。合并文件只改变组织方式，未验证项仍需如实保留。

### 非双端项目怎样对应

保留功能入口、实际实现与验证职责；按项目模块命名实现章节，替换 SPEC 中的两端列与链路，不生成空的客户端/服务端文件。

| 项目形态 | 实现记录关注什么 | 验收观察点示意 |
|---|---|---|
| CLI 或脚本 | 参数解析 → 执行 → 文件或外部操作 | 输出、退出码、文件变化与失败后的残留 |
| 库或 SDK | 公共 API → 内部模块 → 依赖 | 返回值、异常、副作用及受支持调用方兼容 |
| 数据管道 | 输入 → 转换 → 存储/输出，各阶段恢复关系 | 数据完整性、重复与迟到输入、重跑结果 |
| 移动端独立功能 | 界面 → 本地状态/存储 → 系统能力 | 权限、离线、生命周期与本地结果；涉及远端时补实际契约 |

## 方法按需参考

| 你需要补充什么 | 可以借鉴什么 |
|---|---|
| 设计遗漏运行、部署、质量或风险 | 用 arc42 的相关问题检查涉及端的实现说明；不要求复制完整章节 |
| 人、系统、应用和数据存储关系难以说明 | 在功能入口或相关实现说明按需画 C4 视图，标清范围、职责和关系；不要求四层齐全 |
| 后来的人需要知道为什么这样选 | 在相关实现说明记录方案、理由、代价和验证方式；跨端取舍在功能入口留摘要和链接。独立决策确有维护价值时才用 ADR/MADR |

PRD 和技术设计文档是内容载体，TDD（测试驱动开发）是方法，均不是每次必须生成的文件。SDD 可指设计文档或规格驱动开发，使用时说明具体含义；团队已有名称继续沿用。

上述方法的版本、实读范围与限制见 [来源说明](../docs/SOURCES.md#文档实践的定向核对)，按问题查阅的设计片段见 [异步导出](../examples/L3-complex-feature/README.md)。
