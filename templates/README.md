# 模板选择

模板是信息提醒，可删除不适用章节、合并记录或使用等价的任务工具。普通功能默认一份 SPEC；拆分条件与维护责任统一见 [流程](../docs/WORKFLOW.md#约定与文档选择)，不要求填写全部字段或登记文档等级。

## 各文档解决什么问题

| 模板 | 内容职责 |
|---|---|
| [TASK](TASK.md) | 小改动的目标、边界与检查；可放任务卡或 PR |
| [SPEC](SPEC.md) | 单份功能约定：需求、Context、必要设计、验证与结果 |
| [PRD](PRD.md)（Product Requirements Document） | 为谁解决什么问题、业务规则、范围与可验收结果 |
| [SDD](SDD.md)（本 SOP 指 Software Design Description） | 如何实现：责任、契约、运行与部署、取舍和风险 |
| [TEST-PLAN](TEST-PLAN.md) | 用什么场景、环境和资源验证哪些要求；计划与实际结果分开 |
| [DELIVERY](DELIVERY.md) | 汇总实际交付版本、证据、偏差和限制 |
| [ADR](ADR.md)（Architecture Decision Record） | 值得长期保留的重要选择、理由、后果与复查条件 |
| [PROJECT-RULES](PROJECT-RULES.md) | 项目接入时的实际命令、边界和团队要求 |

TDD 通常指 Test-Driven Development（测试驱动开发）：用失败测试、实现、重构的反馈循环推进代码，不是必须提交的 TDD.md。若团队用 TDD 表示 Technical Design Document（技术设计文档），在本 SOP 映射为 SDD，避免两份重复设计。SDD 也可能指 Specification-Driven Development（规格驱动开发）；讨论方法时写中文全称，文档链接中的 SDD 指设计说明。方法名与文件名不是同一个层次，实读来源见 [来源登记](../docs/SOURCES.md#文档实践的定向核对)。

SRS（Software Requirements Specification，软件需求规格说明）适合需要明确软件行为与约束的交付；若客户或项目指定 SRS，按该要求组织，PRD 引用它或由它承载对应软件需求，避免重复。RFC（Request for Comments，征求意见提案）的作用是讨论尚未决定的方案；讨论可以留在现有 SPEC、SDD 或 PR，需要长期保留的重要结论再引用 ADR。这些名称没有新旧替代关系。

## 怎样采用成熟方法

下表是本 SOP 的裁剪建议，正式来源、版本和阅读限制见 [来源登记](../docs/SOURCES.md#文档实践的定向核对)。这些方法补充现有文档内容，不形成另一套强制文件包。

| 方法 | 在本 SOP 中怎样用 | 何时可以省略 |
|---|---|---|
| arc42 架构内容框架 | 在 SDD 中按需要解释系统边界、运行过程、部署、质量目标和风险 | 局部改动无需写全系统架构；不照搬全部章节 |
| C4 视图 | 跨系统关系难以用文字说清时，在 SDD 引用或绘制系统上下文、容器视图；容器指应用/数据存储等运行单元，不等于 Docker | 不要求画全四层；几句话已能说明就不画 |
| ADR / MADR | 为重要选择记录替代方案、后果及如何检查实施是否符合决定 | 常规可逆实现细节留在 SPEC/SDD |
| 可由工具读取的接口契约 | HTTP API 可用项目支持的 OpenAPI；其他通信使用项目已有 Proto/Schema 等，SDD 链接版本并解释业务语义 | 不为没有接口变化的任务新建契约；契约存在不证明实现符合它 |

更规范的关键是信息准确、职责清楚、能关联验证并随实现更新。ISO 的需求、架构描述和测试文档标准可用于核对项目明确要求；本 SOP 未做逐条符合性审计，不宣称模板通过认证，也不把修订草案当成已发布要求。

复杂任务也不必机械创建完整文件包。某个内容已经由任务系统、CI 或接口定义维护时直接引用。复制后删除无用提示，不把空表当交付。可以对照 [异步导出设计示例](../examples/L3-complex-feature/SDD.md) 看需求、运行路径与检查如何衔接；示例尚未实施。
