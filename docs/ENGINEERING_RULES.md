# 工程规则：代码、验证与评审

按本次改动与实际风险选择适用内容。遵循目标项目的语言、格式、权限和发布要求；本文不规定统一测试数量、覆盖率、注释比例或固定 Agent 编排。完成判断集中在 [流程](WORKFLOW.md#评审交付对齐与完成判断)。

## 可维护的代码

通过命名、类型、边界和清楚的结构表达意图，避免把多条关键语句压在一行。改动聚焦目标，不顺手重写无关模块。错误处理符合项目约定，不能吞异常或默认成功来掩盖未完成逻辑。

公共接口、数据或配置变化检查调用方、默认值、版本兼容与失败语义。生成代码、Schema、迁移和契约定义保持明确来源，手写文档引用它们，避免维护另一份机械副本。

## 注释与性能说明

注释解释原因、约束与不变量，重点包括复杂业务规则、生命周期、并发、缓存、兼容处理及必要接口副作用。显而易见的控制流不需要逐行翻译。临时兼容和 TODO 应说明移除条件或相关任务；失真注释随代码修正。

不强制每个方法都写 Big-O。非平凡算法、热点、易退化路径需要有依据的规模与复杂度说明；数据库、网络和异步流程优先说明外部调用次数、批量上限、最坏扇出、分配量和锁等待。无法证明的结论不猜测。

```text
示意：一次批量查询；内存随 pageSize 增长；不持锁执行外部 I/O。
说明成立的规模和条件，实际优化时用测量支持结论。
```

重要性能优化先定位瓶颈，再比较适用环境下的前后结果。格式问题优先使用项目已有工具；人工和 AI 评审把精力用于行为、约束与设计。

## 验证覆盖与方法

验证围绕改变的行为与主要失败后果安排，文档规模不决定验证强度：

| 变化或风险 | 应考虑的验证 |
|---|---|
| 核心规则、缺陷、数据转换 | 正常、边界、非法输入和相关回归；适合时测试先行 |
| 界面与用户操作 | 主要路径、失败反馈和必要人工/端到端检查 |
| 跨模块或 Client/Server | 契约、错误映射、旧端兼容和适用联调 |
| 状态、并发、生命周期 | 重复操作、取消、重试、资源释放、恢复与竞态 |
| 迁移或难回滚变化 | 数据兼容、迁移/回滚或替代恢复方案 |
| 权限、安全或敏感数据 | 越权、数据边界、日志泄露和项目要求的专项检查 |
| 热点或性能目标 | 代表性规模、测量条件与回归影响 |

以上是思考线索，不是每个任务必跑的完整清单。简单文档改动检查文档即可。测试用例应能区分正确与错误行为，避免只复述实现；不要为了绿色结果删除有效测试或削弱约定目标。

测试命令成功不代表发现了足够测试或覆盖了所有验收项。检查实际结果与相关断言，必要时说明测试发现数、具体场景、执行环境和源码版本。已有 CI 报告可直接引用；手工验证记录操作、观察与限制。未执行与部分完成如实说明，不存在适用于所有任务的“完整测试”证明。

## 设计、契约与分端协作

产品意图保留一个权威来源。SPEC 可在同一文档覆盖 Client/Server；只有双方需要独立维护设计时才拆 CLIENT-SDD / SERVER-SDD，两端引用同一可执行契约。

Client 关注界面状态、输入、资源与生命周期；Server 关注业务规则、持久化、事务、并发、幂等和可观测性。纯服务、脚本、数据或其他项目使用对应模块划分，不强行套两端模型。重要兼容、失败恢复和数据边界在现有设计记录中说明。

## 评审与清理

评审优先查目标遗漏、错误行为、失败路径、契约变化、兼容和验证缺口，再看结构与注释。独立评审要有足够上下文与可检查对象；AI 评审也有能力边界，不能保证穷尽问题。高影响或难回滚变化按项目规则安排具备责任的独立判断，不以作者自评代替。

提交前清理临时代码、调试开关、无效日志、死分支和过期注释，更新受影响的说明。交付用已有记录说明实际结果、偏移与遗留。模板中的示例措辞不能作为已执行结果。
