# 从工作流搭建到排行榜重构：实践复盘报告（公开整理版）

版本：v1.0-public

日期：2026-09-16

内部资料观察截止：2026-09-16 09:36（北京时间）

用途：用一次真实工程实践改进工作流。具体实施提案见 [全流程优化方案](../plans/2026-09-16-workflow-optimization.md)。

本文由同日完整内部复盘报告整理，保留工作流演进、完整操作主线、用户纠偏、正负结果和证据边界。为适合公开仓库，移除内部路径、会话标识、私有资料链接、源码符号、专有业务规则、运行环境细节及原始证据；因此不是原报告逐字副本。

**核心发现：流程最值得补强的部分，是让项目事实、适用经验和工具反馈在关键设计与写码决定发生时起作用，并让这些决定随版本、工作副本和后续任务正确传递。**

## 1. 复盘目标与材料边界

这套实践同时追求三个目标：

1. 从需求到交付有清楚、可以接续的工作流程。
2. AI 在理解工程、组织状态、选择结构和处理失败时写得更好。
3. 用完整真实任务检验方法，然后根据收益与使用成本修订流程。

本次内部复盘查阅了相关历史任务、SOP 与执行支持说明、研究手册、独立试验报告、排行榜功能与分端文档、验证汇总和收尾记录，并定向核对部分研究原文。内部保留了 16 份核心资料快照与哈希，以及所读历史消息摘录。

本次没有重新完整审计业务源码、重跑游戏测试或逐篇完整通读全部研究原文。以下运行数量引用历史记录；原始业务证据未公开，外部读者不能仅凭本页独立验证或复跑这些结果。没有进行统计意义的效率或因果效果证明。

另有后续界面修改在观察截止时仍进行中，因此已经记录的最终自检只是一个验证批次，不自动覆盖后续源码。

## 2. 体系分工：每部分帮助什么

| 部分 | 负责的事情 | 不能替代什么 |
|---|---|---|
| Workflow-SOP | 组织需求、边界、设计、实现、反馈和交付 | 项目业务判断和实际工具运行 |
| 项目规则与事实 | 本地架构、规范、真实调用、数据和兼容条件 | 不能仅因旧代码存在就视为优秀设计 |
| 代码质量方法 | 把事实、经验和风险转成生成时的动作 | 不能仅靠“高质量”口号产生能力 |
| 原生工具与执行支持 | 搜索、编辑、编译、测试、版本及记录 | 工具通过不自动等于整体验收 |
| 文档与经验维护 | 恢复当前规则、重要决定、实际结果和限制 | 不能成为与源码分叉的第二套事实 |

实践曾建立完整的目标文档链，随后又收敛日常入口。理论完整与日常轻量可以同时成立：文档职责应解释清楚，独立文件数量按任务裁剪。

还应区分通用 SOP 和某个具体 Harness 的实现。通用说明可以允许裁剪，具体执行系统可能仍有自身状态或评审规则；文档更新不能被当成自动取消程序门禁。

## 3. 演进过程

| 阶段 | 实际诉求与行动 | 带来的变化 |
|---|---|---|
| 建立流程 | 梳理需求理解、功能拆解、设计、实施循环、测试、Review 和清理 | 各环节有记录和模板 |
| 细化约定 | 明确 Markdown、客户端/服务端分工、注释、必要复杂度与工作区 | 资料更适合后续维护 |
| 衔接执行支持 | 明确边界、版本、工具反馈、中断恢复和验收 | 区分完整理论与当前可用能力 |
| 收敛入口 | 多次精简重复文档，统一功能入口与四类职责 | 减轻阅读和维护负担 |
| 排行榜重构 | 从显示异常追到数据、状态、同步、查询及界面链路 | 业务规则与实现一起重新梳理 |
| 工程迭代 | 增补完整性核对、运行验证、代码清理、迁移与文档合并 | 暴露正常路径之外的问题 |
| 独立质量试验 | 恢复旧工程，允许参考已有实现，完整重写比较 | 取得若干具体实现差异 |
| 研究目的纠偏 | 从最终检查转回生成前与生成中的工程判断 | 整理质量手册、实施步骤和工具边界 |
| 全流程复盘 | 保留用户纠正、返工和未验证部分 | 形成下一版优化依据 |

这些工作有重叠，不能把历史整理成一次顺畅的线性成功。用户多次纠偏是本次最有价值的过程证据。

## 4. 完整实际操作主线

~~~mermaid
flowchart TD
    A["需求或问题现象"] --> B["核对实际副本、版本、指令与已有修改"]
    B --> C["查业务链和关键事实"]
    C --> D["明确规则、范围和可观察验收"]
    D --> E["选择适用经验，确定设计与质量约束"]
    E --> F["实现一个业务增量"]
    F --> G["检查、反馈与工程复核"]
    G --> H{"发现的问题"}
    H -->|"事实不足"| C
    H -->|"业务变化"| D
    H -->|"设计错误"| E
    H -->|"实现错误"| F
    H -->|"可继续"| I{"完整范围已覆盖"}
    I -->|"否"| F
    I -->|"是"| J["整体回归、清理和文档对齐"]
    J --> K["开发交付、必要迁移与测试移交"]
    K --> L["适用的验收、提交、发布与观察"]
    L --> M["判断收益与成本，更新或退役经验"]
    M -.-> C
~~~

此图是复盘整理的工作关系，不代表案例自动跑过全部执行系统命令。

| 环节 | 应取得的输入 | 实际工作 | 留下什么 |
|---|---|---|---|
| 开工 | 用户目标、项目位置、已有资料 | 确认完整交付单位、副本、规则与改动 | 简短现场与边界 |
| 事实核查 | 源码、协议、配置、日志和文档 | 找状态拥有者、生产者、消费者、保存与恢复 | 有来源的事实、推断与未知 |
| 业务确认 | 当前行为与预期结果 | 澄清影响结果的规则，避免用实现代替需求 | 可观察验收与关键决定 |
| 设计 | 事实、风险、参考实现 | 判断复用、状态归属、接口、失败语义和必要结构 | 有理由的工程选择 |
| 生成 | 可验证增量与约束 | 主路径、异常和清理同时展开 | 代码、必要测试及对应记录 |
| 反馈 | 实际代码与有效检查 | 判断事实、设计、实现或环境问题 | 真实诊断、修复和重验 |
| 完整性与清理 | 整个任务差异与相关行为 | 核对遗漏、重复状态、无关改动和注释 | 完整交付与清楚限制 |
| 迁移与接续 | 源目标版本、已有修改和清单 | 保护有效内容，核对补丁及目标状态 | 可恢复的依据和必要重验 |
| 复盘 | 过程、结果与成本 | 判断哪些帮助作用于代码 | 可复用候选经验 |

记录可以合并，不要求用户逐步发令或每步建文件。PRD、SPEC 和设计说明分别回答意图、具体行为和实现方式，已有章节能够承担时直接复用。TDD 是适用方法；执行过测试不等于先前全程使用了 TDD。

## 5. 代码生成质量研究怎样落到操作

研究依次涉及质量定义、生成偏差、上下文与范例、质量契约、领域约束、机械反馈和实际评估。重点最终回到“如何补足项目认知与工程判断”。

采用的质量维度包括：

- 可理解性：概念、状态和副作用顺序清楚。
- 局部性：理解一条规则不必掌握大量无关实现。
- 必要复杂度：每份状态和抽象有当前用途。
- 可验证性：能构造区分正确与错误实现的场景。
- 可演进性：已知变化能定位到合理范围。
- 项目适配：尊重本地框架语义、规范、已有能力与生成来源。

这些维度需要结合业务权衡。文件数、行数、测试数、覆盖率或警告数只能提供线索，不能独立裁决质量。

| 原则 | 应在何时作什么 | 可能改变的写法 |
|---|---|---|
| 状态归属清楚 | 写字段和接口前追关键写路径 | 减少竞争权威与重复业务计算 |
| 复用已有能力 | 设计前核对同职责入口及前提 | 避免局部需求扩成公共框架 |
| 生命周期安全 | 首次写异步方法时处理身份和清理 | 成功、异常及收尾遵守同一归属 |
| 保存可靠 | 首次等待前明确批次、新更新和失败去向 | 防止丢更新或无限重试 |
| 协议兼容 | 修改来源后及时生成并核对消费者 | 减少生成漂移和旧端破坏 |
| 注释有效 | 关键规则形成时写原因、条件和成本 | 后续可以理解为何这样做 |

Skill 是使用这些材料与工具的程序说明。它不能替代真实上下文或实际检查，把相同文字改为 Skill 格式不自动提升能力。关于训练数据偏好等解释仍只是研究假设，不是本案例验证过的模型训练事实。

## 6. 排行榜项目重构的实际过程

### 从显示问题追到状态与时序

原现象是不同界面的积分或名次不一致。历史审查发现：查询侧会重新解释业务服务产生的状态，未知归属被误按旧状态处理；另有数据未加载完就建立缓存、后续没有正确更新的独立路径。

这些是源码与受控复现可以支持的缺陷。原故障账号当时是否由其中某一条单独触发，没有完整生产数据证明。刷新更频繁不能修复错误的状态解释，启动漏数据也不能独自解释数值变化。

### 重新确认业务，再调整职责

用户允许从真实业务重新设计，确认资格、状态继承、实际入场、处罚和休赛展示等关键口径。本公开版不披露具体规则，保留方法上的变化：

- 业务服务拥有真实写入，排行服务维护查询副本。
- 相关状态一起产生和传递，用版本识别旧结果。
- 查询就绪与空结果分开。
- 同次响应中的列表和本人结果保持一致。
- 客户端按窗口、实体和请求生命周期处理结果。

这使范围从页面延伸到必要的业务消费者。每项跨层修改仍需说明必要性，不能以“全链路”为所有公共改造兜底。

### 首版过重，用户推动返工

早期任务曾报告涉及大量文件，随后用户明确指出命名不符合项目规范、文档没有沿用模板、注释不足、公共导出器被改动，以及整体实现过重。

后来实际规则与实现经过调整：正式文档采用 Markdown，沿用功能和分端模板；关键函数记录合理复杂度与 I/O 条件；收缩公共改造和重复状态。

这表明项目约束和范围判断出现得太晚。不能只把缺口归为自检不够：它们本应在第一次生成前进入设计输入。

### 完整性核对继续暴露问题

用户要求画原链路与新链路，逐文件解释必要性，整理全量功能点。进一步发现处罚显示与实际结果不符、公开资料术语混用、外观映射缺失、异常阻断退出清理、旧资料影响分池归属等问题。

临时新增的全链说明和功能清单有助于查漏，但长期维护又与正式手册重复，因此后来按职责合回。

### 代码清理有明确对象

| 视角 | 历史记录的实际处理 |
|---|---|
| 结构简化 | 删除重复初始化状态，保留候选、排序与失效各自职责 |
| 失败处理 | 保存失败重新排队，明确批次边界，重复导入不静默采用 |
| 注释与理解 | 写清字段真实含义、复杂度条件、调用次数和失败范围 |
| 保护兼容 | 恢复误删的既有资料复制，收缩纯格式差异 |
| 保留边界 | 通知送达、失败结算补偿等限制继续记录 |

无空异常捕获或有日志，都不能单独证明业务恢复完善。

### 迁移和后续决定产生新的返工

不同工作副本之间曾发生路径混淆、内容丢失和恢复。已有实现做对，也可能在后续会话或迁移中被覆盖。需要按源、目标、基线和具体补丁判断，不能只依赖“上一任务已完成”。

某次恢复旧匹配行为又被用户质疑，最后按明确指定的局部改动回退。中间建议不能覆盖最后有效决定；恢复某次变化也不能等同整文件还原。

界面展示顺序及手动刷新交互后来发生调整，对应旧测试必须标历史。后续仍在进行的修改，不由前一轮“最终自检”自动覆盖。

## 7. 独立 B 版试验与项目线必须分开

质量方法的准备最初偏向任务集、工具、严格实验和最终判定。用户随后明确：以整个排行榜重写为一次实践，从重写前旧工程恢复，允许参考已有答案，先判断生成前/生成中是否有帮助。

| 对象 | 含义 | 不能混同的状态 |
|---|---|---|
| 旧基线 | 真实重写前完整工程，早期错误起点后来已纠正 | 不能使用含部分重写的版本冒充起点 |
| A | 当时已有实现的冻结参考快照 | 不持续跟随项目最新版 |
| B | 独立副本中的完整重写，复用部分已确认契约与链路 | 没有自动同步回项目 |
| 项目后续版 | 另外发生的迁移、修复和运行验证 | 不能将其测试记到 B |
| 后续 Skill/手册 | 在 B 后继续整理的方法 | 不能把旧 B 当作新方法已重新运行 |

历史比较报告记录了以下具体差异：

- 周状态在时间变化情况下更清楚地保持单调。
- 完整状态变化时一同更新版本。
- 针对可覆盖快照的一个批次，减少重复保存尝试。
- UI 初始化异常进入统一清理范围，使请求可以恢复。
- 在试验采用的旧数据预期下保留信息。

其中旧数据处理与目标项目后来的规则存在前提差异，不能因为 B 比较称为改善就直接合回。保存去重也只适用于相应状态性质，不能套到必须逐条执行的交易或事件。

B 的记录支持具体实现差异及有限验证，不支持新 Skill 的因果效果。新 Skill、统一手册和生成示例形成得更晚；示例部分是事后解释，并未重新完成一轮新方法完整生成。

## 8. 用户纠偏说明了什么

| 纠偏 | 暴露的流程问题 | 应提前放到哪里 |
|---|---|---|
| 不符合项目命名与模板 | 通用习惯覆盖本地约定 | 开工读取与首个新增结构 |
| 只改一个功能却影响很多内容 | 必要关联和额外治理混合 | 设计范围及公共改动必要性 |
| 不要受旧实现限制 | 把现状当作设计答案 | 事实与目标分开 |
| 列全功能点和原新链路 | 主路径掩盖消费者和失败遗漏 | 设计时按状态与行为核对 |
| 要整个功能重写 | 评测方案改变用户任务单位 | 开工固定交付范围 |
| 无须刻意盲化 | 严格研究前置过重 | 区分实用实践与严格实验 |
| 生成的时候就控制 | 最终检查替代生成辅助 | 首次设计与关键写法反馈 |
| 资料没有真正读完 | 阅读覆盖和结论强度不一致 | 如实声明阅读，重要方向回原文 |
| 迁移后内容丢失 | 副本与多人修改衔接不清 | 迁入前后核对和补丁级恢复 |
| 文档太多 | 分析视角变成重复长期文件 | 最终按职责合回 |
| 上线交给测试联调 | 单一“完成”承载太多状态 | 区分开发交付、验收和发布 |

内部没有可靠的总人工分钟、净节省时间或标准化纠正次数。本页不把表格行数当介入次数，也不虚构 ROI。正常业务澄清不能一概算作浪费。

## 9. 实际结果与限制

### 项目线的已记录批次

历史机器汇总记录了 136 项检查通过：服务链 35、重启 2、白盒 58、数据库故障注入 9、客户端异步/快照 24、关联 UI 联动 8。另有数值边界、随机更新和独立排序对照，不能混算为更多独立验收项。

服务器普通及分析器编译通过；客户端普通编译通过，项目分析器仍有与基线一致的历史错误，关联完整旧测试仍有失败。原失败未被专项成功覆盖。协议生成一致性得到相应批次检查。

最后自检又发现并修复 UI 初始化异常卡住请求的问题。B 中曾处理过相似缺陷，但 B 没自动合回，因此不是同一版本的重复验证，也说明经验传递没有闭合。

### 尚未完成的范围

当时尚缺当前真实 UI 资源/点击、完整客户端与地图/跨服务生命周期、生产数据升级回退、正式目标构建、按业务指标的容量性能判定，以及覆盖最终版本的独立人工 Review。没有据此执行项目发布。

方法替身能控制异常和交错，不证明真实渲染；实际数据库测试不证明生产数据升级；容量观测没有业务 SLA 就不能称性能达标。开发侧交接可以带着明确缺口完成，不能冒充发布验收。

### B 版的验证独立保留

B 记录了服务端源码编译、受控方法比较和排名核心检查。当时未执行真实游戏、数据库、UI 资源及端到端跨服务联调。项目线之后的结果不能补写到 B。

### 三种结论强度

| 结论 | 当前支持程度 |
|---|---|
| 某处实现改善 | 有具体例子和对应历史验证 |
| 某项帮助影响本次生成选择 | 有部分过程描述，需要更准确的当时使用记录 |
| 整套方法稳定有效且有净收益 | 还缺可比任务、成本、重复运行和长期维护证据 |

复盘还发现验收文档顶部已更新结果，底部仍残留旧批次状态。报告按原始汇总解释该批次，并将重复状态维护列为改进问题，没有掩盖来源矛盾。

## 10. 文档和工作区的最终组织

| 载体 | 长期职责 |
|---|---|
| 功能说明 | 当前共同规则、范围、关键决定、两端与验证入口 |
| 客户端实现 | 界面、数据、请求、生命周期、资源与恢复 |
| 服务端实现 | 校验、业务、状态归属、持久化、并发、接口与失败 |
| 验证与验收 | 当前基线、场景、真实结果、历史证据和缺口 |
| 原源码/协议/配置/测试 | 可执行契约与实际实现 |
| 外部任务与证据 | 过程、迁移依据、原始输出、快照和复盘 |

四类文档不要求四个固定文件：已有章节与格式可以对应，小修复可沿原任务。共同规则只维护一份，两端解释如何满足；文档不是字段和源码的机械副本。

项目内容、过程资料、验证证据和临时文件按实际工作区约定分开。后续修改先读功能入口，再核对源码和最后决定，判断旧证据是否适用，更新受影响部分。

## 11. 优先改进顺序

第一优先是补工作衔接，而非新建平台：

1. 开工固定任务对象、现场、有效规则和最后决定。
2. 从关键事实形成几条能影响设计和写码的约束。
3. 第一处高风险写法形成时取得反馈，再扩展同类实现。
4. 新增公共改动说明必要性与替代方案。
5. 验收只维护一个当前摘要，历史批次保留原始依据。

随后补经验与接续：

- 将已修问题变成带前提的候选范例或反例。
- 分清参考经验、可移植补丁和目标是否已应用。
- 迁入前核对目标新修改，迁入后作必要重验。
- 记录实质纠偏和额外负担，没有数据就承认未知。
- 根据实际收益更新或删除方法。

只有反复缺口明确且可可靠判断，才增加结构检索、自动触发或分析器。更多 Prompt、Skill、JSON 或 Gate 本身不构成质量提升。

## 12. 下一次怎样检验

下一次真实任务沿原 SOP 推进，少量保留：

| 记录 | 能回答的问题 |
|---|---|
| 完整范围、版本与参考使用 | 是否真的在做同一件事 |
| 某条事实改变了某项设计 | 上下文是否影响生成 |
| 范例前提与选择理由 | 是否合理迁移经验 |
| 首次反馈时机与代码修正 | 是否阻止错误扩散 |
| 实际结果、失败与未测范围 | 结论是否匹配证据 |
| 额外阅读、工具和维护负担 | 方法是否值得保留 |

先判断业务正确和设计合适，再讨论方法作用和成本。单次改善可以支持局部经验，不能证明普遍稳定收益。

具体文件、分批实施、兼容方式和验收场景见 [全流程优化方案](../plans/2026-09-16-workflow-optimization.md)。这份报告是维护参考，不成为每次开发的必读材料。
