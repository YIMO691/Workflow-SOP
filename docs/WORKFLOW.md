# 工作指南：从提单到持续维护

供 AI 和开发者共同使用。收到任务后按本页推进，相关细节按需查阅；用户无须先学习方法名称或配置整套工具。原生 AI 工具负责搜索、编辑、命令和上下文执行。

## 开始工作

1. **核对现场**：确认目标项目、实际指令、提单与授权，检查有关代码、接口、配置和测试。已有信息自行查，不要求用户重新描述。
2. **找到记录**：查项目文档目录、已有任务和 PR，找到当前功能说明。新功能没有合适记录时，用 [四部分模板](../templates/SPEC.md) 在项目允许的位置建立；已有格式直接沿用。
3. **确认当前要交付什么**：记录目标、范围、可观察的验收和主要失败行为，区分事实、假设与未决方案。只问影响当前业务结果、重要契约或授权的问题，并说明选择与代价。
4. **开始推进**：当前增量的目标、必要方案、验证方式与授权清楚就实施。普通技术细节可边做边确认，无依赖的已授权工作继续；阻断项只暂停受影响动作。

项目已有规则、实际权限和用户授权继续有效；业务取舍、技术风险、验收、合并及发布由项目实际责任人承担。AI 不编造批准或风险接受，也不增加每阶段统一审批。来源读不到时说明缺口，不假装已读；项目边界缺失时才参考 [项目约定](../templates/PROJECT-RULES.md)。

## 完整链路

详细 [Mermaid 流程图](../README.md#整个流程) 集中在首页：提单 → 核对现状与记录 → 明确实施条件 → 实现与验证循环 → 文档对齐与评审 → 提交及后续修改。需求、实现、验证与变更信息更新在同一份文档；条件与异常处理以本页为准。

## 维护功能说明

**实际开发默认留痕，同一功能优先维护同一份说明。** 复用现有记录，不把每次提单变成一套新文档。

| 情况 | 写在哪里 |
|---|---|
| 新功能 | 已有合适文档，或一份新的功能说明 |
| 功能扩展、规则或设计变化 | 更新原功能说明，关联本次提单或 PR |
| 独立小修复 | 在原提单或 PR 说明目标、改动与验证；影响已记录的功能行为或设计时同步该文档 |
| 仅解释、咨询或探索 | 按实际需要记录，明确提案未实现，不自动生成开发文档 |

普通功能默认交付 `功能名.md`，如 `收藏功能.md`；`templates/SPEC.md` 只是模板名。已有项目文档格式继续沿用。功能文档放在目标项目已有文档位置，使用稳定、易辨认的功能名称，并加入相关模块索引或项目入口；提单/PR 链接它，文档的变更记录链接相关任务。没有提单系统时可在变更记录简记来源和日期，不为留痕强制新建 Issue。

### 四部分怎样更新

| 部分 | 开始时 | 随实施及交付更新 |
|---|---|---|
| 需求与边界 | 来源、已有行为、本次目标和验收；未实现部分明确标为本次拟变更 | 核对最终约定，将已实现行为更新为当前说明，未完成目标继续保留去向 |
| 实现说明 | 查到的模块、代码入口、必要方案和重要理由；待实施方案与现状分开 | 更新实际调用/数据关系、主要失败处理和选择理由，移除失效方案但保留重要变更原因 |
| 验证与遗留 | 要检查什么、预期依据、环境前提及未知 | 写实际场景、版本/环境、结果与证据；失败、未验证和后续事项明确保留 |
| 变更记录 | 引用当前提单或简记本次工作，注明进行中 | 简记实际改动、原因与结果，关联最终 PR/证据；平台已有状态直接引用 |

### 保持文档有效

- 正文解释当前功能，本次拟变更、已实现但未验证、待决定内容明确区分；不把草稿写成既成事实。
- 后续只改受影响章节，保留有效内容、人工补充和重要理由。历史差异由 Git/任务记录承载，变更记录只写对维护有用的摘要，不复制完整旧正文或聊天。
- 引用实际代码路径、接口定义、测试和证据；文件移动或接口改变时更新引用。不要抄写可生成字段或逐行解释源码，避免多处同步。
- 结果对应本次变更；旧证据不覆盖新行为时明确标注并重验，不能只修改日期。已完成、已验证、已合并和已发布分别表述。
- 文档无法写入时，交付明确说明尚未落档的内容及补齐位置，不以聊天摘要冒充已经更新。多人修改时核对版本与差异，保留他人有效修改。

同一文档确实难以由相关人员维护时，才把需要独立维护的部分拆出，原位置改为引用。默认不分别创建需求、设计、测试、交付和决策文件；方法提示见 [文档用法](../templates/README.md)。

## 实施与变化处理

按一片可观察的行为安排实现与验证，记录真实依赖；小任务可以一次完成，跨模块任务保留集成责任。支撑性迁移不能单独证明业务验收。测试先行适合时采用，验证方法由行为和风险决定，见 [工程规则](ENGINEERING_RULES.md)。

| 遇到什么 | 怎样继续 |
|---|---|
| 实现细节调整，目标与重要契约不变 | 自主推进，同步有维护价值的设计变化 |
| 行为、范围、授权或重要契约改变 | 找实际责任人协调，在原文档更新约定与受影响范围 |
| 测试发现实现错误 | 修实现并重验，不能删断言或改目标来制造通过 |
| 环境、依赖或测试自身有问题 | 先定位前提和预期，按授权修复后再查；未能执行就记录未验证 |
| 反复失败但没有新证据 | 说明已尝试内容，调整诊断路线；停止盲目重跑 |

计划违背已确认需求时，应在原目标内修正计划与实现；真正改变业务要求才重新协调。需求、代码、契约和文档有变化时一起核查受影响的验证，其他仍适用的成果保留。具体诊断见 [失败排查](ENGINEERING_RULES.md#检查没有给出结论时)。

## 交付与后续

实施者先自检；按项目责任与风险评审，高影响或难回滚变化需要适当独立检查。同一作者换一段提示词不构成独立评审。提交前核对：

- 本次目标是否实现，主要失败、兼容与权限问题是否处理。
- 实际验证能支持哪些结论，关键缺口是否仍阻断交付。
- 功能文档是否反映最终实现，提单、代码及证据是否可找到；必要清理是否完成。

提交物通常是代码及相关测试的改动，加上新增或更新的功能说明；独立小修复按上方记录规则处理。代码与文档随同一次工作提交到目标项目已有位置，不把业务资料提交到本 SOP 仓库；项目已有明确交付要求时沿用。在原任务或 PR 汇总改动、文档入口、验证与未完成项即可，不另写交付报告。检查缺失或失败就说明尚未完成；不阻断的限制由项目实际责任人决定是否接受。编译成功、测试通过或文档齐全都不能自动证明全部验收。最终验收、合并与发布沿用项目方式和授权。

### 中断与交接

在原任务或文档的“验证与遗留”补足：当前版本与未提交改动、完成范围、重要决定、实际证据、未决项及下一步；已有内容直接引用。恢复者核对现场、权限和已发生的外部动作，再从未完成处继续。结果未知的写入或发布先核实，不盲目重复执行；暂停不写成完成。

### 发布后的观察与反馈

需要发布新行为时，在原发布/任务记录注明观察对象、范围与时段、异常触发、实际接手人与处置权限，引用已有监控和值班安排。关键风险无人接手时暂停相关发布；文档等无运行影响改动可省略运行观察。

发布失败或发现异常时保留版本与脱敏事实，按授权回退、停用或修复，再更新受影响的需求、实现与验证。观察尚未结束就写明观察中及后续入口，不提前宣布运行验证通过。参考 [异步导出的运行风险](../examples/L3-complex-feature/README.md)。

### 用实际任务修订流程

发现重复记录、无效等待、漏检或交接困难，在原任务保留具体情况，再按 [贡献指南](../CONTRIBUTING.md) 提出删减或修订。没有固定试用数量、代理数量或文件配额；一次任务顺利完成不证明普遍效率提升。
