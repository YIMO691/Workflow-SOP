# 工作指南：从提单到持续维护

供 AI 和开发者共同使用。收到任务后按需参考本页，相关细节按问题查阅；用户无须先学习方法名称或配置整套工具。原生 AI 工具负责搜索、编辑、命令和上下文执行。

人与 AI 先用项目事实对齐当前目标，文档随实施承载规则、选择和验证依据；发现偏差就修正，交付后继续从原功能入口维护。

## 执行速查

输入是当前任务、操作边界和可读取的项目；已有需求、实现与证据由执行者查找。完整链路保留在 [首页流程图](../README.md#整个流程)，细节按 [读取表](../README.md#给-ai-的执行入口) 定位。

| 当前要做什么 | 留下什么或据此怎样继续 |
|---|---|
| 查项目指令、相关代码、原功能入口与证据 | 确认当前行为、拟变更、影响范围和未知项；见 [开始工作](#开始工作) |
| 对齐本次需求和验收 | AI 整理 [最小充分需求](#整理最小充分需求)，按 [未知分流](#未知怎样处理) 补缺口；用户只处理缺少依据的重要决定 |
| 判断能否实施当前增量 | 核对 [最小方案](ENGINEERING_RULES.md#最小方案与复杂度) 和 [验证条件](#提前核对验证条件)；条件清楚就推进，缺口只阻断依赖它的动作 |
| 实现一片行为并验证 | 更新受影响的原记录；按 [变化处理](#实施与变化处理) 区分实现、需求和测试前提问题，再修正与重验 |
| 自检并核对交付 | 用 [交付条件](#交付与后续) 核对目标、证据和维护入口；按项目安排处理评审、验收、合并与发布 |
| 结束或交接 | 在原任务/PR 说明实际结果；中断按 [交接要求](#中断与交接) 留下可恢复的现场 |

交付说明沿用项目格式，至少能找到：**改动与完成范围；功能/代码维护入口；实际验证及其版本、证据；失败、未执行或待决定项及下一步。** 已实现、已验证、已合并和已发布分别表述。上述动作可以连续完成，记录可合并；不要求用户逐段发令或新增报告。

## 怎样裁剪

个人习惯决定怎样组织工作；改动的影响和项目要求决定需要验证什么。裁剪先复用现有成果，再合并或省略不适用的步骤。

| 可以灵活安排 | 需要保留的结果 |
|---|---|
| 步骤顺序、计划详略、工具与协作方式 | 当前目标、范围和重要约定清楚，行动符合项目授权 |
| 文档篇幅、独立文件或已有章节 | 后来的人能找到有效规则、相关实现、选择理由和验证依据 |
| 单元、契约、人工或联调等验证方式 | 证据能检查改变的行为及主要失败后果，未验证范围明确 |

先问：已有记录能否承载本次变化？涉及哪些规则和实现？是否出现 [工程验证触发条件](ENGINEERING_RULES.md#验证覆盖与方法)？前两问决定补哪里，后一问决定查什么。例如只改显示文案可复用原提单与界面检查；权限、持久数据或契约变化按对应触发条件处理。记录组织见 [按现状选择载体](../templates/README.md#按现状选择载体)。

## 开始工作

1. **核对现场**：确认目标项目与实际工作副本、版本、未提交改动、最后有效决定、指令和授权，明确交付单位是完整功能、局部修复还是研究比较；检查有关代码、接口、配置和测试。已有信息自行查，不要求用户重新描述。
2. **找到记录**：查项目文档目录、已有任务和 PR，找到功能入口及相关两端实现、协议和验证。缺少记录时按 [模板用法](../templates/README.md) 补齐涉及的文档；已有格式直接沿用。
3. **确认当前要交付什么**：记录目标、范围、可观察的验收和主要失败行为，区分事实、假设与未决方案。只问影响当前业务结果、重要契约或授权的问题，并说明选择与代价。
4. **开始推进**：当前增量的目标、必要方案、验证方式与授权清楚就实施。普通技术细节可边做边确认，无依赖的已授权工作继续；阻断项只暂停受影响动作。

项目已有规则、实际权限和用户授权继续有效；业务取舍、技术风险、验收、合并及发布由项目实际责任人承担。AI 不编造批准或风险接受，也不增加每阶段统一审批。来源读不到时说明缺口，不假装已读；项目边界缺失时才参考 [项目约定](../templates/PROJECT-RULES.md)。

验收句应让另一位执行者在给定前提下操作，并能区分满足与违反规则的结果；写明观察位置，如界面、响应、文件或最终数据。数量由不同规则、边界和失败后果决定，不设 AC 条数门槛；“正常、合理、体验好”需要补成可裁决结果。见 [验收正反例](../examples/decision-examples.md#验收只有评价词)。

需要责任人决定而对方暂不可达时，在原任务写明待决定项、受影响动作与恢复条件，沿用项目通知或交接安排；继续无依赖且已授权的工作。未回复不等于同意，也不自行创造审批期限。

### 整理最小充分需求

由 AI 根据用户原话、有效决定和已核实的项目事实，在原需求或任务中整理能支持当前增量实施与验收的内容。最小充分需求（MSS）是信息是否够用的判断，不是交给用户填写的新表单。围绕以下问题补实际缺口：

| 需要明确什么 | 整理到什么程度 |
|---|---|
| 目标与可观察结果 | 谁在什么情境下做什么，哪里能看到预期变化 |
| 不变量与约束 | 必须始终成立的业务、权限、数据、兼容和操作边界 |
| 沿用行为 | 哪些现有规则继续有效，其依据在哪里；不把现状自动当正确需求 |
| 范围与非目标 | 这次涉及什么，哪些相邻需求明确不做；必要依赖不能当作非目标省略 |
| 验收与关键未知 | 前提、动作、独立预期及必要失败行为；还缺哪个决定或验证条件 |

这些内容可以是一段话，也可放入原 [功能说明](../templates/SPEC.md#需求与边界) 的对应章节，不强制每项单列。技术细节留在实现记录。当前增量没有会改变结果的重要歧义、能写出区分对错的检查、行动已获授权时，就开始实施；无需等全部后续细节完备。发现新约束时再更新相关内容，局部需求充分不等于完整任务已完成。

### 未知怎样处理

先查与当前决定相关的入口及其直接依赖；取得足够依据后停止扩展阅读。文档与代码不一致时查有效决定、版本和测试，不用重复搜索代替判断，也不因文件较新就默认业务语义正确。

| 剩余未知 | 执行动作 | 留下什么 |
|---|---|---|
| 项目内可查事实，如状态归属、配置、既有接口 | 自行查证；读不到时说明具体缺口，继续无依赖工作 | 影响决定的路径、符号或证据，避免抄全文 |
| 已有目标与授权内、影响局部且易恢复的技术选择 | 沿项目惯例自主决定并检查；涉及重要契约或数据后果时不能只因代码易回退就自行猜定 | 仅保留有维护价值的理由 |
| 会改变业务结果、重要契约或授权，且无现成决定 | 提出聚焦问题，给出实际行为差异、建议和代价；只暂停依赖该决定的动作 | 待决定项、影响与恢复条件；不重复询问有效授权 |
| 没有当前依据的未来可能需求 | 不实现预留框架；有保留价值时简记重新考虑的触发条件 | 非目标或后续线索；已确认的兼容承诺和排期约束仍需评估 |

确需在不阻断的假设下推进时，只记录会影响行为、结构或验证的假设：**假设是什么、依据和影响、如何查证，以及何时必须重新检查。** 一句即可，不建立琐碎选择台账。关键业务或授权缺口不能借“假设”绕过。新事实推翻假设时回到受影响的决定与检查，不在错误前提上继续补丁。见 [未知分流示例](../examples/decision-examples.md#同一个需求里的不同未知)。

### 提前核对验证条件

方案形成时查实际构建、定向测试和运行入口，以及依赖、账号、资源、工具权限、日志和临时输出位置。原项目指南有记录就引用；命令存在只证明找到入口，实际运行结果才说明它在当前环境可用。以最小、已授权的检查及早发现环境缺口，不为确认环境而直接发布或写入生产数据。

按 [行为和风险](ENGINEERING_RULES.md#验证覆盖与方法) 选择观察层次。缺少工具、依赖、环境或写入权限时，做仍可执行的检查，在原验证记录说明哪项行为未验证、具体恢复动作和接手安排；不擅自安装、绕过限制或用静态检查冒充运行结果。条件恢复后执行对应场景，只有其他证据确实覆盖同一要求时才能调整方法。模板只提示记录位置，不能赋予工具能力。

## 完整链路

唯一的 [完整流程图](../README.md#整个流程) 集中在首页：用户意图 → 项目查证 → 未知分流 → 最小充分需求与验证条件 → 最小方案与复杂度核对 → 实现和反馈 → 完整范围验证与必要评审 → 开发交付 → 按授权发布及持续维护。动作可以合并；功能说明关联涉及端的实现和验证，复用原记录。

### 目标能力与完成边界

这次优化的目标，是让用户给出任务及关键约束后，AI 能在项目既有授权内完成查证、设计、实施、验证和记录更新；用户集中处理重要业务取舍、授权缺口及必须由人判断的效果。用户无须学习研究术语、穷举边界或逐步下令。以下定义目标能力，不表示所有项目已接入自动检查，也不表示采用收益已经得到验证；实施进度见 [优化方案](plans/2026-09-16-workflow-optimization.md#12-本次交付边界)。

| 目标能力 | 实际应做到什么 | 怎样判断达到 |
|---|---|---|
| 从简短意图开始 | AI 根据用户原话与项目事实整理目标、可观察结果、关键不变量、沿用行为、范围和验收；只补影响实施的缺口 | 用户无需重新描述可查事实；形成的行为约定可以据此实施与验收 |
| 自主处理未知 | 项目事实自行查；低影响、局部可逆选择自主决定；没有当前依据的未来需求暂不实现；缺少关键业务、重要契约或授权决定才升级 | 提问说明实际行为差异和为何查不到；已有决定与授权不重复询问 |
| 保持必要的设计 | 先复用现有能力，核对其适用性；新增抽象、状态、依赖和公共改动说明当前问题、简单方案及不足 | 每项重要结构都对应当前需求或项目不变量；不以想象中的未来功能为唯一理由 |
| 尽早得到反馈 | 方案阶段查验证入口、环境与权限；首个关键增量取得相关反馈，再完成所有受影响的端、消费者和场景 | 缺陷在适用范围内修复并重验；当前实现已满足要求时可以只核查，不为体现方法而改代码 |
| 用对应证据判断完成 | 验收预期来自需求和可信项目约定；按行为选择编译、静态、自动化、联调或实际运行证据 | 编译不替代动画播放，桩测试不替代真实依赖，历史通过不覆盖新版本；未验证范围明确 |
| 交付后可以继续修改 | 在原功能入口与任务中对齐规则、涉及端实现、重要决定、当前版本及证据；小修按原载体留痕 | 后续执行者能定位实现和缺口并继续工作，不必重新阅读整段聊天 |
| 用实际成本修订流程 | 记录可取得的返工、漏验、可避免提问及人工阅读、答复、审查、验收时间 | 收益与额外负担一起判断；无数据标未知；无收益机制可以删减 |

**完成程度由当前任务目标和证据决定。** 开发交付包含实现、相关测试及有效维护记录；若约定的关键行为缺少必要验证，相关范围仍为待验收，不能报告整体完成。外部环境不可用时，先做其他可行工作，在原记录写清已完成部分、具体缺口、恢复动作及接手安排，按 [中断与交接](#中断与交接) 继续。合并、发布及观察另按实际需要和授权处理，不是每个任务的默认动作。

工作强度随风险调整：局部可逆且惯例明确的修改，合并查证、修改与检查；普通功能补足必要需求和方案；跨端状态与复杂交互加强契约和联调；持久数据、破坏性兼容及难回滚变更按项目要求落实必要决定、恢复安排和检查。它们不构成固定等级协议或文档配额，详见 [怎样裁剪](#怎样裁剪) 和 [工程触发条件](ENGINEERING_RULES.md#验证覆盖与方法)。

Workflow-SOP 提供规则、模板、示例和文档检查；原生 AI 工具负责执行，目标项目提供真实源码、构建、测试及运行环境。稳定且可判断的规则在目标项目已有检查中逐步落实；本仓库不因此扩建 Agent 运行平台。一次规则更新只证明指引已改变；工具是否能执行、实际任务是否满足验收、长期是否减少人工负担，分别取得证据。

## 维护功能说明

**功能说明是统一入口，双端功能分别维护客户端实现、服务端实现和验证与验收。** 这些内容共同解释需求到实现的链路，后续提单继续更新原文件；已有项目格式、分端手册和测试记录直接对应，不重复创建。

| 情况 | 写在哪里 |
|---|---|
| 新双端功能 | 功能说明、客户端实现、服务端实现、验证与验收；已有记录先复用 |
| 扩展或修改功能 | 梳理完整链路后更新受影响的原文档，变更摘要关联提单/提交 |
| 仅一端的功能 | 功能说明、涉及端的实现及验证；注明另一端未涉及的依据 |
| 独立小修复 | 原提单或 PR 说明目标、改动和验证；影响已有行为或设计时同步原文档 |
| 仅解释、咨询或探索 | 按实际需要记录，明确提案未实现，不自动生成开发文档 |

文件放在目标项目已有文档位置，使用稳定的功能名称，如“收藏功能-功能说明.md”和对应分端文件。功能说明加入项目/模块索引，链接两端实现与验证；其余文档链接回入口。提单或 PR 链接入口，重要变更摘要反向关联任务及最终提交。没有提单系统时简记来源和日期，不为留痕强制新建 Issue。跨仓库分别记录实际版本与获准访问的链接，不复制私有资料到本 SOP。

### 各文档怎样更新

| 文档 | 开始时 | 随实施及交付更新 |
|---|---|---|
| [功能说明](../templates/SPEC.md) | 来源、目的、当前规则、拟变更、验收与端职责；建立关联入口 | 对齐最终约定和完整链路，保留关键规则到两端/契约/验证的对应关系，记录重要变更原因 |
| [客户端实现](../templates/CLIENT.md) | 界面与状态、调用链、代码入口、同步与恢复方案 | 核对实际交互、数据与失败处理，保留理由和限制，链接对应场景 |
| [服务端实现](../templates/SERVER.md) | 校验、业务、数据归属、并发与兼容方案 | 核对实际处理、存储及恢复边界，保留理由和限制，链接对应场景 |
| [验证与验收](../templates/VERIFICATION.md) | 规则对应的场景、预期来源与环境前提 | 记录实际版本、结果、证据及未验证项，复查旧结果适用范围和重验需求 |

共同规则在功能说明维护，端内实现解释“怎样做到”，协议/配置/Schema/测试源码引用项目原定义。开始时先写清当前增量的规则、必要方案与验收场景；实现细节随工作核实，交付时对齐实际状态。载体选择见 [文档用法](../templates/README.md)。

### 保持文档有效

- 正文解释当前约定与实际实现，本次拟变更、已实现但未验证、待决定内容明确区分；不把草稿写成既成事实。需求与代码冲突先核实，不以现状覆盖原意。
- 后续只改受影响章节，保留有效内容、人工补充、截图和重要理由。历史差异由版本控制/任务记录承载，变更摘要不复制完整旧正文或聊天。
- 记录实际代码路径、关键符号和版本，说明调用关系；文件或接口改变时更新引用。多个仓库分别记录 Git 提交、SVN 修订或项目已有版本标识。
- 验证结果对应具体实现、契约和环境；旧证据不覆盖新行为时标记待重验，不能只改日期。已实现、已验证、已合并和已发布分别表述。
- 文档无法写入时说明尚未落档内容及补齐位置，不以聊天摘要冒充已更新。多人修改时核对版本与差异，保留他人有效修改。

### 后续让 AI 修改同一功能

1. **从入口恢复需求**：读功能说明中的当前规则、边界、重要决定与提单变化，沿链接读取相关两端实现和验证缺口。
2. **用代码核实文档**：检查实际版本、共同协议/配置、关键调用和测试。查不到或不一致时明确差异；文档是定位入口，不能替代代码核查。
3. **梳理本次影响**：按受影响规则检查客户端、服务端、契约、数据及验证。看似只改一端也要核对另一端的假设；未影响的部分给出依据，不强制修改所有文件。
4. **实施并同步记录**：先区分当前与拟变更，再更新相关规则、实现、对应关系和场景；实现改变后复查旧证据，保留仍适用的结果。
5. **逐项核对交付**：从验收规则沿链接走到两端、契约和实际结果，查漏项、断链、过期描述与未验证风险。不能把链接齐全当作行为正确。

例如“收藏上限改成 100 条”需要核查客户端提示、服务端原子限额判断、返回语义与并发验收；只改需求数字不足以交付。具体写法见 [收藏功能的后续修改](../examples/L2-standard-feature.md#后续提单怎样修改)。

## 实施与变化处理

按一片可观察的行为安排实现与验证，记录真实依赖；小任务可以一次完成，跨模块任务保留集成责任。支撑性迁移不能单独证明业务验收。测试先行适合时采用，验证方法由行为和风险决定，见 [工程规则](ENGINEERING_RULES.md)。

### 把研究用到一次代码生成

任务涉及代码生成质量改进时，将相关研究或复盘中的建议落实为下面的动作。普通任务按风险取用，不必先读研究库、安装 Skill 或另建质量报告。研究提供候选方法；项目事实和实际检查决定能否采用。

| 时机 | AI 实际执行什么 | 留下可核对的结果 |
|---|---|---|
| 准备作设计决定 | 从本次行为找状态写入方、消费者、既有机制及适用规范；只读影响决定的资料 | 实际路径/符号与版本，已核实的事实及尚缺什么 |
| 准备首次实现 | 选与当前风险有关的方法，核对来源与前提；写清它将影响哪项选择 | 在原设计记录简记“事实/方法 → 实现选择 → 如何检查”，无适用方法也如实说明 |
| 第一处关键写法形成 | 完成一个包含成功、相关失败和清理的业务增量；按工程规则取得 [首个增量反馈](ENGINEERING_RULES.md#生成时的工程判断) | 真实诊断和行为结果；阻断同类扩展的问题先修复，其他授权工作可继续 |
| 反馈与预期不符 | 核对测试前提；事实不足补查，设计不合适改设计，局部错误改代码，业务变化协调原约定 | 哪项事实或哪次检查改变了哪处实现；相关重验结果 |
| 扩展到完整范围 | 将已核实的选择应用到适用消费者，检查新增前提，完成集成、评审和文档对齐 | 完整交付范围与当前证据；局部增量不冒充整个任务完成 |
| 判断方法是否保留 | 在原任务记录实际帮助及额外成本；未观察到作用也记录 | 具体决定和代码变化，不以读过资料、提示词长度或测试数量证明方法有效 |

执行者可连续完成，不要求用户发六轮指令。关键未知涉及业务或授权时才按 [开始工作](#开始工作) 协调；材料失效或来源读不到时不冒称使用。现有格式能承载就直接复用，不强制表格或条数。

第一次采用可照 [异步刷新操作示例](../examples/decision-examples.md#把异步研究变成一次实现)：先确定观察行为，再查实际机制、实现、检查与修正。教学反例用于理解动作，不能记为真实项目验证或模型效果实验。

### 变化发生后

| 遇到什么 | 怎样继续 |
|---|---|
| 实现细节调整，目标与重要契约不变 | 自主推进，同步有维护价值的设计变化 |
| 缺少关键事实，或状态/依赖设计不合适 | 补查对应入口或修正设计，再改实现；不能仅靠局部补丁绕过错误前提 |
| 行为、范围、授权或重要契约改变 | 找实际责任人协调，在原文档更新约定与受影响范围 |
| 测试发现实现错误 | 修实现并重验，不能删断言或改目标来制造通过 |
| 环境、依赖或测试自身有问题 | 先定位前提和预期，按授权修复后再查；未能执行就记录未验证 |
| 反复失败但没有新证据 | 说明已尝试内容，调整诊断路线；停止盲目重跑 |

计划违背已确认需求时，应在原目标内修正计划与实现；真正改变业务要求才重新协调。需求、代码、契约和文档有变化时一起核查受影响的验证，其他仍适用的成果保留。具体诊断见 [失败排查](ENGINEERING_RULES.md#检查没有给出结论时)。

## 交付与后续

实施者先自检；独立检查按 [评审触发条件](ENGINEERING_RULES.md#评审与清理) 安排。提交前核对：

- 本次目标是否实现，主要失败、兼容与权限问题是否处理。
- 实际验证能支持哪些结论，关键缺口是否仍阻断交付。
- 功能入口是否能沿关键规则找到实际两端实现、契约和对应证据；相关版本是否一致，遗漏/不适用是否说明，必要清理是否完成。

按 [维护功能说明](#维护功能说明) 的职责提交本次受影响的代码、测试和记录，放在目标项目已有位置；交付说明见 [执行速查](#执行速查)。关键目标未实现、权限/数据/兼容约束被违反，或对应验证仍缺失时，标明受影响部分未完成；不阻断的限制由项目实际责任人决定是否接受。最终验收、合并与发布沿用项目方式和授权。一次完整的轻量交付见 [真实维护案例](../examples/completed-maintenance.md)，其文档检查不代表业务验收。

### 中断与交接

在原任务或验证与验收文档补足：实际副本和版本、暂存/未暂存及新文件、完成范围、最后有效决定、实际证据、进行中动作、未决项及下一步；已有内容直接引用。恢复者核对新发生的差异、权限和外部动作，再从未完成处继续。结果未知的写入或发布先核实，不盲目重复执行；暂停不写成完成。

切换副本、迁入改动或选择性回退时，分别固定源与目标版本和未提交状态，明确获准迁移的内容、目标已有修改及恢复依据。执行前再查目标是否变化；按具体差异应用、保留无关有效改动，不能用整文件旧副本覆盖后来工作。无法可靠分离时先补清差异。完成后检查受影响链路并重验；哈希只能证明指定快照相同。代码回退无法恢复数据或外部副作用时，另按 [迁移验证](ENGINEERING_RULES.md#验证覆盖与方法) 处理。

### 发布后的观察与反馈

需要发布新行为时，在原发布/任务记录注明观察对象、范围与时段、异常触发、实际接手人与处置权限，引用已有监控和值班安排。关键风险无人接手时暂停相关发布；文档等无运行影响改动可省略运行观察。

发布失败或发现异常时保留版本与脱敏事实，按授权回退、停用或修复，再更新受影响的需求、实现与验证。观察尚未结束就写明观察中及后续入口，不提前宣布运行验证通过。参考 [异步导出的运行风险](../examples/L3-complex-feature/README.md)。

### 用实际任务修订流程

试用或发现重复记录、无效等待、漏检、交接困难时，在原任务补一段采用反馈：**SOP 版本与任务类型；具体问题和结果；下一次保留或改变什么。** 复用已有案例和检查，其他流程或旧版本的结果需核对适用条件。

研究转成操作后，补一句实际关联即可，例如“初始化异常场景发现保护范围遗漏，因此将初始化纳入清理范围，并重验失败后可再次请求”。若只是事后解释、没有当时使用记录，不追认为方法导致改进；例子成立也不证明 AI 更稳定或整个方法有净收益。

有记录时一起观察结果和成本，不把少提问、少代码或短用时单独当作成功：

| 观察面 | 原任务可记录的信号 |
|---|---|
| 正确性与边界 | 需求偏差、漏验、遗漏的重要升级、缺陷和回归；正常迭代与错误返工分开 |
| 人工总投入 | 阅读、回答、纠偏、审查、人工运行验收和维护记录的时间；可避免提问与必要澄清分开 |
| 结构与后续修改 | 无当前依据的新增状态、抽象、依赖；以后改同一规则时涉及的同步位置与返工 |
| 执行代价 | 有条件时记录工具等待、运行费用及检查维护成本，避免把成本转移后称为节省 |

说明统计起止、任务范围和原因，区分估计、实测和未知，不追补虚构数字。需要比较时选需求与风险相近的任务，记录项目、SOP、工具/模型版本和可取得的环境条件；先约定要改善什么及不能退让的正确性边界。有归因需要再重复运行或逐项移除候选机制比较，不设统一任务数、收益百分比，也不让日常开发等待实验。

经验复用须带来源版本、适用前提、影响的选择、实际结果和失效条件。发现无帮助、成本过高或前提变化时缩减、调整或退役；项目已有知识入口能承载就不另建经验库。

改进建议沿用 [现有反馈入口](../CONTRIBUTING.md#提出问题或修改)，注明预期改善、额外成本与下次确认方式。真实小修复、双端功能及后续维护分别积累证据，教学例子不充当采用结果；一次任务顺利完成不证明普遍效率提升。
