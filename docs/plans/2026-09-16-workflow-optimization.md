# Workflow-SOP 全流程优化方案

日期：2026-09-16

状态：部分实施于当前分支；已补研究用于生成的最小操作、工程判断、模板提示与可运行教学示例。其余方案待实施，真实项目采用效果待验证；分支内容不等于已合并或发布。

核对基线：main 的 b6b7f772ac99a82c194b3593fcc9a69d7141e48b。

依据：[排行榜实践复盘（公开整理版）](../reports/2026-09-16-workflow-retrospective.md)。

## 1. 优化目标

让工作流更直接地帮助 AI 理解工程、作设计和写代码，同时减少后期纠偏、重复记录及接续丢失。最终仍交付符合需求的代码、相关测试和可持续维护的记录。

此次案例显示：流程执行完整不保证设计合适；测试和文档齐全也不能说明某项生成方法有效。下一版要把实际帮助放到关键决定发生之前或当时，并保留少量可检查的关联。

优化分为五个方面：

1. **需求与现场可靠。** 完整任务范围、实际副本、有效指令、关键业务决定能被正确恢复。
2. **生成前有依据。** 根据状态归属、已有能力、消费者与失败条件选择结构。
3. **生成中反馈及时。** 第一处关键写法取得适用检查后，再推广到相关位置。
4. **交付与接续不丢失。** 代码、文档、当前证据和迁移目标对应同一现场。
5. **经验可以复用和淘汰。** 知道什么帮助改变了哪项决定，以及适用前提和额外成本。

保留轻量、工具中立、模型自主的定位。四类文档是职责，不设必交文件数；不增加 Agent runtime、任务数据库、统一审批或固定代理角色。

## 4. 开工与设计：让项目事实改变选择

### 开工留下什么

在已有任务或功能入口中，用必要篇幅说明：

- 这次完成什么，属于完整功能、局部修复、实用比较还是严格研究。
- 实际工程位置、版本和已有修改；跨仓库或工作副本分别核对。
- 当前生效的项目规范、文档格式、SOP 采用方式和版本。
- 必须保持的行为、授权边界、可观察验收及关键未知。

能够从工程找到的事实自行查。某一份流程入口缺失时，先判断影响什么，只暂缓依赖它的决定；继续无依赖的已授权工作，不冒称已经读取。

### 按决定查事实

| 准备作什么决定 | 需要查什么 | 形成的设计依据 |
|---|---|---|
| 状态放在哪里 | 关键写路径、持久化与恢复、派生副本 | 唯一所有者和更新边界 |
| 是否新增能力 | 同职责入口、调用方、已有机制的前提 | 复用、局部扩展或新建的理由 |
| 如何划分接口 | 生产者、消费者、版本和默认行为 | 兼容范围与必要映射 |
| 如何写异步流程 | 等待期间会变化的实体、窗口、请求及资源 | 成功、异常和清理的有效性条件 |
| 如何保存与重试 | 状态性质、提交点、批次、失败与重复 | 能否覆盖、去重、重放及恢复 |
| 是否需要抽象或缓存 | 当前变化原因、规模、读取/写入成本 | 当前收益、额外状态和维护代价 |

事实与建议分开。旧代码用于了解当前行为，不能仅因存在就当作认可范例；不要求全仓通读。

### 质量约束融入原设计记录

在“重要决定”“失败恢复与取舍”等已有章节记录能影响本次生成的约束，不建立强制 QUALITY-CONTRACT.md，也不要求固定条数。

推荐写法：

> 依据已核实入口，业务写入仍由其拥有者处理；查询副本只消费结果。首个同步增量完成后检查新旧数据顺序，再展开展示。

避免仅写“遵守最佳实践、简洁、可维护”。有真实分歧时比较直接方案与必要替代方案，说明新增状态、层次或公共机制解决什么当前问题；不凑方案数量。

新增消费者可能是完成业务所必需，文件多不是自动失败。公共导出器、存盘框架或无关领域改造，应单独说明必要性与替代方案。实现细节自主处理，业务范围、重要契约或授权变化沿项目实际责任关系协调，不增加每阶段审批。

## 5. 生成中反馈：把最后的补救提前

### 三类触发时机

| 触发点 | 生成动作 | 首个增量的适用反馈 |
|---|---|---|
| 首次引入状态、权威边界或跨模块写入 | 明确所有者、提交顺序、失败后状态 | 正常、重复和部分失败；判断有无重复规则 |
| 首次引入异步等待、保存批次或资源生命周期 | 主路径和异常清理一起形成 | 迟到结果、对象变化、等待中新更新或初始化异常 |
| 首次修改协议、Schema、配置来源或兼容行为 | 改权威来源并更新必要消费者 | 原生成链、兼容核对、目标编译和针对性场景 |

按风险选择，不要求每次编辑运行完整工程。文案或机械修改只做必要局部检查。适用时沿用测试先行，不能把既有开发追认为 TDD。

### 根因回流与最小记录

- 事实缺失、错误或过期：补查上下文。
- 业务目标或规则变化：更新原功能约定，核对受影响部分。
- 状态、依赖或结构不合适：修改设计后再实现。
- 局部实现错误：修复并重验。

环境和测试自身问题先核实前提与预期。没有新证据时调整诊断路线，不靠重复运行直到通过。

值得留下时，在原设计或验证记录增加一句“来源/诊断 → 决定变化 → 代码或行为结果 → 限制”。记录工程结论和真实动作，不要求输出内部推理，也不强制建表。事后教学例子不能充当当时的生成记录。

## 6. 整体验证、清理与交付

### 完整性按受影响行为核对

围绕相关业务链，按风险考虑正常、非法输入、失败、重复、乱序、生命周期、兼容、资源和性能。沿实际生产者与消费者查遗漏，复用已有 AC、测试与文档链接。

不是每个任务都填完整矩阵。小修只检查相关行为；复杂任务先确定关键状态和边界，再选择验证。

### 清理用三个视角

1. 结构：重复状态、无收益抽象、规则分散、纯格式噪声和无关改造。
2. 失败：吞错、默认成功、通知与业务提交混淆、失败后丢更新、清理被异常阻断。
3. 可理解性：失真命名与注释、隐藏兼容条件、未经证明的复杂度或性能说法。

这些是现有 Review 的关注点，不新增三个强制角色或独立报告。兼容字段和已有用户修改不能因清理被顺手删掉。

### 当前验收状态只保留一个入口

在已有验证文件“结果与遗留”中维护当前摘要，历史批次引用原证据：

- 区分编译、静态检查、方法替身、真实依赖、用户端到端和生产演练。
- 说明基线、配置/协议、场景及未覆盖范围。
- 行为改变后，仅对应范围的旧证据待重验；其余有效证据说明依据后复用。
- 自检、独立评审、开发交付、业务验收、合并和发布分别表述。
- 不把工具 CI 或文档检查当作业务效果证明。

模板不预填 PASS。历史错误和旧测试失败保留归因与当前影响，不删断言或禁用规则制造全绿。

## 7. 接续、迁移与经验回流

### 中断恢复

恢复前核对最后有效决定、当前版本、未提交改动、已执行外部动作、进行中工作及旧证据适用范围。原任务有记录则直接引用。

曾接入 SOP、曾编译通过、上一条说已完成，都需要核对对应现场。资料不能访问时明确缺口，不补造读取或授权。

### 迁移或选择性回退

在原迁移/任务记录中说明源与目标各自版本、允许迁入的清单、目标已有变化、保护与恢复依据。迁入前复查目标是否有新修改；之后核对受影响内容并选择必要重验。

回退时定位具体语义差异，避免整文件恢复删掉其他有效改动。哈希用于核对指定快照一致性，不能证明业务正确，也不代表后续目标永久一致。

### 经验携带适用条件

候选经验记录问题、来源版本、前提、决定、结果及不能照搬的条件。例如可覆盖状态的批次去重，不直接适用于每条都必须执行的事件。

经适用性核实与实际反馈再认可；过期、误导或无收益时更新或退役。优先复用项目已有知识入口，不默认新建 Golden 数据库或全局 Skill。

## 9. 分批实施与验收

| 批次 | 工作与依赖 | 完成条件 | 回退或缩减 |
|---|---|---|---|
| P0：复盘与方案（已交付） | 核对 main、公开报告、文件级方案和导航；纠正访问描述 | 文档检查、公开内容审阅、分支/PR；方案不冒充实施 | 撤销本次文档提交，不触碰现行规则 |
| P1：主干衔接（部分实施） | 当前聚焦研究到生成的操作；其余 WORKFLOW、ENGINEERING_RULES 和 README 衔接待补 | 下节场景能找到动作、依据与回流；无重复权威和统一审批 | 缩短过重部分或按提交恢复；保留入口 |
| P2：模板与例子（部分实施） | 已补对应原模板提示及异步例子；其余 P1 语义确定后继续对齐 | 从需求到设计、生成、反馈及后续修改读通；无新必填配额 | 删冗余提示，沿用原文件和标题 |
| P3：真实采用 | 在已授权任务中使用 P1/P2，记录版本与条件 | 说明哪些输入影响哪些决定、结果和成本；允许无改善 | 无收益步骤降级/删除，不凭单次成功宣布成熟 |
| P4：工具增量（有证据才做） | P3 暴露反复且可可靠判断的缺口 | 明确输入、触发、诊断和误报边界；正确/错误样本均有效 | 回到人工/原生工具，不扩大为运行平台 |

P1 与 P2 可在一个聚焦 PR 中连贯完成；批次表示依赖和审查单位，不要求用户每一步重新授权。采用反馈不足时保持试行，不用版本号替代成熟度。

每批按整个批次的基线到最终版本审差异，包含新文件与工作区变化；不只看最后提交。实施阶段的发布、合并沿用实际授权。

## 10. 如何验证方案没有再次走偏

### 文档与行为推演

这些是后续方案验收场景，不是本次已运行的业务测试，也不要求新建自动评分器。

| 场景 | 优化后应发生什么 | 不应发生什么 |
|---|---|---|
| 只改文案 | 沿原提单修改并作必要局部检查 | 完整质量契约和四份空文档 |
| 状态同步 | 查真实写入方与查询副本再选接口 | 每层复制业务计算 |
| 新异步请求 | 首次方法形成时处理身份和清理，作适用反例 | 正常路径写满全链后才补生命周期 |
| 保存失败 | 查状态性质、批次及等待中新更新再选去重/重试 | 对必须逐条执行的事件盲目去重 |
| 完整重写实践 | 保持完整范围，参考使用如实记录 | 擅改成小题或强制盲化 |
| 切换副本或回退 | 核对最后决定、目标差异与具体补丁 | 用旧目录或整文件恢复覆盖新工作 |
| UI 交互变化 | 受影响场景重验，旧点击测试标历史 | 只改日期继续称当前通过 |
| 旧测试失败 | 核实预期、环境和实现，保留边界 | 改断言迎合实现 |
| 经验与规则冲突 | 核实前提，必要时拒绝复用 | 范例曾通过就强行合入 |
| 参考资料不可访问 | 说明缺口，继续无依赖授权工作 | 冒称完整阅读或阻塞全部 |

### 仓库检查

运行既有 scripts/validate-workflow.ps1，核对文档、标题、文件链接和主要锚点。本方案不要求改检查器。

只有确需改检查器时，按贡献指南在仓库外临时目录跑有效包和损坏输入回归。不能用字数、函数行数、关键词或文档数量自动裁决业务质量。

### 真实任务的效果与成本

在原任务保留可取得的信息：任务类型与版本、实质纠偏及原因、早期发现的问题、后期返工、实际验证、额外阅读/维护负担。没有记录写未知，不编造节省时间或收益比例。

先看实现正确和设计合适，再看方法贡献与成本。正常澄清不是浪费；不能为少提问而猜业务，也不能为少返工而漏验。

需要比较稳定性时再选可比任务、重复运行或消融，不把它们作为日常开发的开工条件。

## 11. 兼容与采用

- 老项目沿用已有文件名、模板和版本策略，不需整体迁移文档。
- 有效项目门禁、权限、评审和兼容承诺继续适用。
- 主规则只在 WORKFLOW/ENGINEERING_RULES，模板只给位置提示，案例解释用法。
- 只读咨询和低影响修改保持轻量，跨端、持久化和时序按真实风险展开。
- 方案和报告是可选维护资料，不加入每次任务的默认必读列表。
- 改重要标题或路径时维护旧入口去向；当前方案不提出目录重组。
- 未经真实采用验证的方法保持试行，可缩减或退役。
